# CSRF в проекте BFF: три подраздела и три Eraser-схемы

Дата: 16.10.2026. Статус: содержание и декомпозиция согласованы в диалоге; письменная спека ожидает ревью.

## 1. Цель

Читатель страницы «Авторизация и CSRF» должен понимать, кто добавляет cookie и заголовки,
какие запросы BFF пропускает, где блокируется запрос чужого сайта и почему внешний переход
по ссылке остаётся разрешённым. Пользователь выбрал три самостоятельные схемы и подраздела:
наш клиент, чужой сайт, переход по внешней ссылке. Новая защита или новый транспорт не проектируются.

Результат — объяснение согласованного будущего BFF, по которому студенты реализуют сервис.
Схемы не объявляются описанием уже работающего BFF. Ссылки для пользователя — на VitePress,
а не на исходники Markdown.

## 4. Содержание схем

### 4.1. Запрос нашего клиента

Пример — защищённая mutation `POST /api/trpc/notebooks.create` с JSON-телом.
Код собственного tRPC-клиента ставит постоянный `X-CSRF: 1` и `credentials: same-origin`.
Браузер сам прикладывает cookie `__Host-Http-session`; JavaScript её не читает.
Для POST браузер задаёт Origin и Fetch Metadata, это не произвольные доверенные значения из тела.

BFF сначала проверяет `X-CSRF: 1`, точное равенство `Origin` и `APP_ORIGIN`, а также
`Sec-Fetch-Site: same-origin`, если заголовок есть. Только после этого читает сессию и вызывает Go.
Проверки выполняются в `createContext`, включая login/register/logout; пример защищённой процедуры
не означает, что у login/register требуется уже существующая сессия.

Схема различает код приложения, браузер и BFF; проверка CSRF предшествует сессии и Go.
Короткая выноска объясняет: `X-CSRF: 1` — не секрет и не случайный токен, а заголовок,
для которого чужому origin требуется разрешение CORS. Отдельного получения CSRF-токена нет.
Успешная CSRF-проверка сама по себе не доказывает наличие действительной сессии.

### 4.2. Атака с чужого сайта

В одной схеме показаны два разных пути, которые нельзя сводить к единому HTTP 403:

- HTML-форма не умеет ставить `X-CSRF`. `application/x-www-form-urlencoded` и `text/plain`
  отклоняются адаптером tRPC как `415 UNSUPPORTED_MEDIA_TYPE` до `createContext`;
  multipart доходит до CSRF-проверки и получает `403 csrf_invalid` из-за отсутствия заголовка.
  Go не вызывается в обоих случаях.
- Cross-origin fetch с `X-CSRF: 1` и JSON вызывает preflight OPTIONS. BFF не выдаёт
  разрешающие CORS-заголовки; браузер не отправляет основной запрос. Отказ preflight
  не изображается ответом 403 на якобы выполненную mutation.

SameSite=Lax не отправляет сессионную cookie на cross-site fetch и POST. Это дополнительный слой,
а не единственная защита. Поддомен может быть same-site, но остаётся другим origin:
Lax не исключает отправку cookie, а заголовок/CORS и точные POST-проверки Origin/Fetch Metadata
остаются обязательными. Для same-site поддомена нельзя обещать, что cookie никогда не отправляется.
Отдельная выноска или компактная ветвь схемы объясняет эту разницу; подробность — в H4 рядом.

### 4.3. Переход по внешней ссылке

Пользователь открывает ссылку GitHub/Telegram в обычном браузере с сохранённой сессией.
Это top-level GET HTML через Caddy в BFF, а не RPC mutation. Cookie Lax передаётся;
`X-CSRF` не требуется и `Sec-Fetch-Site: cross-site` допустим.

HTML-хендлер использует общий слой сессии/refresh и возвращает HTML с BootstrapData:
только пользователь или `user: null`. При действительной сессии пользователя получает общий
Go-клиент; без сессии Go для определения пользователя не вызывается. Стор инициализируется
до первого рендера. Подробную обработку ошибок и сериализацию не дублируем:
ссылка ведёт на существующий раздел bootstrap, правила HTML 503 и cookie сохраняются.

Схема подчёркивает: GET HTML не меняет предметные данные и не выполняет logout.
Последующие RPC снова проходят обычные CSRF-проверки; разрешение GET HTML не отменяет защиту API.
Встроенный браузер другого приложения может иметь отдельное хранилище cookie и оставаться гостем.

## 5. Формат и файлы

Новые JSON: `diagrams/modules/2/bff-csrf-client.json`, `bff-csrf-foreign.json`,
`bff-csrf-navigation.json`. Каждая схема отвечает одному подразделу и не повторяет остальные.
Зоны, легенды, абсолютные координаты с шагом 20 и типы стрелок — по eraser-diagrams и
`scripts/colors.ts`. Не вводятся собственные цвета «разрешено/запрещено».
Узел браузера имеет id `client`; интерфейс BFF не распадается на отдельные развёрнутые сервисы.
Схемы должны быть достаточно компактны для чтения отдельно в HTML/PNG; масштабирование
общего просмотрщика не входит в эту задачу.

Изменяются `site/modules/2/tracks/bff/auth.md`, таблица схем модуля №2 в `README.md`,
`scripts/bff-pages.test.ts`; добавляется один структурный тест трёх схем
`scripts/bff-csrf-diagrams.test.ts`. Старые схемы BFF, ROOT_NAMES, sidebar и текущий
раздел `/security/csrf/` не меняются. Продуктовый код, issues и назначения вне scope.
Исторические спеки не переписываются; WebSocket не возвращается на целевую страницу.

## 6. Проверка и доставка

Тесты страницы закрепляют три H3 в CSRF, H4 поддомена, соответствие имён схем,
сохранение прежних заголовков-якорей и ровно семь оставшихся сценариев сессии.
Тесты графов проверяют существенные пути и подписи: порядок CSRF → сессия → Go,
различие 415/403/preflight, отсутствие mutation после отказа CORS и отсутствие вызова Go
в ветвях атаки. Внешняя навигация отличается от RPC и сохраняет Lax/bootstrap.
Точные координаты тестами не закрепляются.

Для всех трёх схем: validate → check → warm → render → осмотр PNG.
Перед коммитом: modules:check, typecheck, test и build. На собранном сайте проверяются
три подраздела, все схемы и HTML/PNG-ссылки; прежние якоря остаются рабочими.
Это проверка документации, не runtime-тестирование BFF.

После ревью письменной спеки — план и SDD. Ранее разрешённые commit, push и обновление
ready PR #73 сохраняются; merge выполняет пользователь. В ответе даются production-ссылки
VitePress, а до мержа явно отмечается, что новая версия доступна только в preview PR.
