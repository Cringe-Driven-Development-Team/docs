# Публичное пространство четырёх OpenWiki

## Зачем

На `https://docs.cellestial.ru/openwiki/` сейчас опубликована только wiki `docs`.
Четыре wiki уже связаны для локального поиска агентов через MCP, но этот workspace
хранится в `~/.openwiki` и в сборке сайта не участвует. Посетителю нужен тот же общий
вход в знания о проекте: документация, frontend, backend и infra в одном интерфейсе.

Владелец выбрал объединение при сборке Pages. После слияния PR с обновлением wiki
в любом из четырёх репозиториев сайт пересобирается автоматически. Генерация
содержимого остаётся ручной; публикация не вызывает модель.

## Подходы и согласования

1. **Объединять при сборке `docs` — выбран.** Получать четыре wiki, собирать общий
   граф и адаптировать существующий визуализатор. Собственная поддержка ограничена
   сборкой, объединением графов и элементами навигации.
2. **Добавить визуализацию workspace в сам OpenWiki.** Удобно также для локального
   применения, но требует собственной версии пакета или принятия изменений upstream.
   Владелец предпочёл первый вариант.

Согласован интерактивный макет `four-wiki-layout.html`: переключатели
«Все / docs / frontend / backend / infra» сверху, под ними четыре компактных блока
с датой и SHA, список страниц слева, граф в центре, содержимое справа.
Макет хранится локально в `.superpowers/brainstorm/938377-1793481970/content/`;
его данные, количество страниц и связи демонстрационные. Эта спецификация
фиксирует поведение независимо от доступности локального макета.

## Область работы

- Единый адрес `/openwiki/`, общий граф и чтение всех четырёх wiki без установки MCP.
- Фильтр по репозиторию, группировка списка страниц по владельцу, источник каждой
  страницы, дата генерации и исходный SHA каждой wiki.
- Автоматическая публикация после слияния wiki PR, ручной повтор запуска Pages.
- Существующие тема, чтение Markdown, Mermaid, масштабирование/перемещение графа,
  скрытие графа, favicon и дата в московском времени сохраняются.
- В режиме «Все» цвет узлов обозначает репозиторий, как в согласованном макете;
  тип страницы остаётся в заголовке читателя. Это заменяет прежнее раскрашивание
  по типам, а не добавляет вторую конкурирующую легенду.

Планы модулей, генератор wiki, локальный MCP workspace, приложение и его деплой
не меняются. Не создаются пятая wiki, отдельный сервер, поисковый движок,
автоматическая генерация, семантическое вычисление связей или форк OpenWiki.
Макет не добавляет требования отдельного поля поиска; существующий объём
навигации достаточен для этой задачи.

## Источники и воспроизводимая сборка

Список источников фиксирован: публичные репозитории организации
`Cringe-Driven-Development-Team/{docs,frontend,backend,infra}`, каталог `openwiki/`.
Нельзя передать произвольный репозиторий, путь или ref через dispatch payload.

В начале сборки один раз фиксируются полные SHA четырёх checkout:
`docs` — коммит текущей сборки Pages, платформы — их `main` на момент подготовки
снимка. Затем используются только эти коммиты. Одновременный merge может попасть
в следующую сборку; единого атомарного релиза четырёх репозиториев не требуется.
Не брать платформенную wiki из последнего успешного CI: её владелец — Git.

Для каждой wiki различать:

- `repositorySha` — коммит, из которого прочитаны опубликованные wiki-файлы;
- `sourceSha` — `gitHead` из её `openwiki/.last-update.json`, исходники генерации;
- `updatedAt` — дата завершения генерации из checkpoint;
- время сборки сайта — технические метаданные всей публикации.

Видимая дата относится к генерации, а не к скачиванию или выкладке сайта.
Формат: `16:53 31 октября 2026 г. МСК`. Показывать сокращённый SHA, полный доступен
в подписи/ссылке. Ссылка source SHA ведёт к коммиту соответствующего репозитория;
ссылка на сам Markdown — к wiki-файлу на `repositorySha`.
Рядом с выбранной страницей повторяются её владелец, дата и source SHA.

Сборочный manifest содержит все эти сведения и статус свежести по каждому
источнику. Абсолютные локальные пути, `~/.openwiki`, рабочие каталоги CI и секреты
в публичный manifest/граф не попадают. Checkpoint не публикуется целиком:
выбираются только нужные поля.

### Валидность и устаревание

Это предложение автора спеки: завершённая, но устаревшая wiki остаётся доступна,
с заметной пометкой «Исходники изменились после обновления wiki». Сравнивать
checkpoint с зафиксированным коммитом владельца существующими правилами
`openwiki-source-path.ts`/`checkOpenWiki`, а не простым неравенством двух SHA.
Изменение только сгенерированных страниц не должно означать устаревание.
При проблеме определения свежести показывать «Свежесть не проверена» и причину
в отчёте сборки; не обозначать такой источник свежим. Выполнение проверяющего
кода, если оно нужно, допустимо только из доверенных checkout `main`, без токенов
и сохраняемых Git credentials; предпочтительно переиспользовать проверенную
общую логику и данные классификации путей.

Отсутствующие wiki/quickstart, неполный или неверный checkpoint, повреждённый
граф, недоступный репозиторий и невозможность получить зафиксированные файлы —
ошибки сборки. Не выпускать незаметно граф из трёх источников и не брать старую
копию из кэша вместо недоступного источника. Уже опубликованный сайт при неуспехе
сборки сохраняется обычным механизмом Pages.

Ссылки/сообщения об устаревании не объявляют код продовым. Wiki платформ описывают
реализацию на исходном SHA; `docs` направляет к документам и свидетельствам
проверок. Дата wiki не является датой проверки прода.

## Объединённый граф и переходы

Страницы не копируются в каноническую wiki `docs` и не редактируются. Из каждого
источника читается обычный граф OpenWiki; его идентификаторы получают префикс
репозитория: `docs/quickstart`, `frontend/architecture/bff` и т. п. Префикс
применяется также к links, backlinks и рёбрам. Одинаковые пути и заголовки разных
wiki остаются разными страницами.

Внутренние относительные Markdown-ссылки разрешаются в пределах своей wiki.
Межрепозиторные рёбра создаются только из явных ссылок на существующие страницы
wiki другого подключённого репозитория. Поддержать канонические GitHub-ссылки
вида `https://github.com/Cringe-Driven-Development-Team/<repo>/blob/<ref>/openwiki/<page>.md`
для `main` и зафиксированного `repositorySha`; ссылка на иной ref остаётся внешней,
чтобы не подменять историческую страницу текущей. Ссылки на исходный код,
рукописные документы и другие сайты остаются внешними ссылками.
При отсутствии межрепозиторных ссылок граф может содержать четыре компоненты:
искусственные рёбра по похожим словам, тегам или предполагаемой архитектуре
не добавляются. Связи демонстрационного макета в продукт не переносятся.

Переход на страницу и её раздел должен работать из списка, узла графа и текста
другой страницы. Якорь раздела сохраняется и прокручивает читатель к заголовку.
Добавить стабильный URL страницы с репозиторием, относительным wiki-путём и
необязательным разделом, восстанавливаемый после перезагрузки; конкретное
кодирование fragment/query оставлено исполнителю. Не создавать отдельный
физический HTML-файл для каждой wiki-страницы. Без параметров открывается
`docs/quickstart`, фильтр «Все». Неизвестный адрес даёт понятное состояние
«Страница не найдена» и переход к карте, а не произвольную другую страницу.

## Интерфейс и адаптация

- «Все» показывает полный граф и список, разделённый на четыре группы. Выбор
  репозитория оставляет в графе и списке только его страницы и внутренние связи.
- При смене фильтра выбранная страница сохраняется, если принадлежит этому
  репозиторию; иначе открывается его quickstart. «Все» сохраняет выбранную страницу.
- Переход по ссылке в другую wiki открывает её страницу. Если действует фильтр
  другого репозитория, переключает фильтр на владельца цели, как в макете.
- Четыре блока дат остаются видны при фильтрации; неактивные можно приглушить.
  Каждый блок также выбирает свой репозиторий. Фильтрация не изменяет даты.
- Короткие заголовки списка сопровождаются названием группы, полный путь
  доступен в читателе. Названия репозиториев текстовые: цвет не единственный
  способ отличить источник.
- На узком экране фильтры и метаданные переносятся; граф можно скрыть, чтение
  и переключение страниц остаются доступны. Макет разрешает скрывать граф
  автоматически, конкретные пороги и размеры — решение исполнителя.
- Клавиатурная навигация, видимый focus, активный фильтр и читаемый контраст
  обязательны. Не убирать существующую sanitization Markdown/HTML.

Основной визуальный ориентир — установленный OpenWiki и согласованный макет.
Refero Linear Changelog использован только как дополнительный ориентир для
компактных фильтров и типографического разделения дат/кода; его маркетинговая
композиция и нейтральная палитра на интерфейс не переносятся. Сохраняются
нынешние тёмные поверхности, светлая тема и палитра узлов OpenWiki.

## Публикация и права

`docs` продолжает запускать Pages после push в `main`. В `frontend`, `backend`
и `infra` добавить небольшой workflow на `push` в `main` с изменёнными
`openwiki/**`, который вызывает `workflow_dispatch` существующего `docs/pages.yml`
на `main`. Это покрывает merge и разрешённый прямой push с wiki-изменениями;
закрытие PR без слияния, push в рабочую ветку и обычное изменение кода платформы
не запускают новую публикацию через этот workflow. Payload источника допустим
для журнала, но не задаёт checkout, команду или репозиторий.

Обычный `GITHUB_TOKEN` платформенного репозитория не принимается за право запуска
workflow в другом репозитории. Предлагается отдельный secret `DOCS_PAGES_TOKEN`:
fine-grained token с доступом только к `docs`, Actions write; доступен трём
платформенным workflow. Других привилегий для чтения публичных wiki не нужно.
Это выбор автора спеки для минимального объёма настройки, а не уже выданное
согласие на создание учётных данных. При внедрении проверить доступный механизм
и подготовить secret; не копировать пользовательский локальный токен и не
расширять права `ADD_TO_PROJECT_PAT` молча. Пока межрепозиторный dispatch не
работает, автоматическая публикация не считается принятой.

Ошибка вызова Pages видна как ошибка workflow, а не зелёный no-op. В логах —
репозиторий/коммит источника и результат запуска без токенов. Одновременные
события используют существующую очередь Pages `cancel-in-progress: false`;
отдельный сервис очереди/дедупликации не нужен. Существующее расписание Pages
для сайта и доски остаётся, новые таймеры не добавляются.

Источник платформенных wiki подготавливается один раз на запуск Pages,
вне временных checkout веток `docs`. Основная сборка и превью получают один
снимок платформ, а собственную wiki `docs` читают из своего checkout. Это
предотвращает скачивание трёх репозиториев заново на каждую ветку. Локальная
команда экспорта умеет явно получить те же публичные источники и фиксирует
их SHA; не зависит от наличия соседних студенческих клонов или личного workspace.
Выбор каталога снимка и способ передачи в Docker/превью — задача исполнителя.
Токены dispatch в Docker и сборку страниц не передаются. Публичные файлы читаются
как данные; скрипты, hooks и установку зависимостей платформ ради экспорта
не запускать.

## Приёмка

1. На `/openwiki/` доступны завершённые wiki всех четырёх источников. Количество
   страниц соответствует снимкам, нет конфликтов `quickstart`/`index`.
2. Фильтры, список, выбор узлов и переход между wiki работают как описано;
   одинаковые имена, `.md#section`, кириллица, пробелы и кодирование URL проверены.
3. Видимые даты/source SHA совпадают с checkpoint владельцев, manifest содержит
   полные source/repository SHA. Дата сайта и статус свежести не подменяют их.
4. Реальные внутренние и поддержанные явные межрепозиторные wiki-ссылки дают
   корректные рёбра/переходы. Исторические ref и ссылки на код остаются внешними.
5. Нет секретов и локальных абсолютных путей в HTML/JSON. Markdown sanitization
   сохраняется; ссылки не позволяют выйти из разрешённых источников при сборке.
6. Повреждённый/отсутствующий источник роняет сборку до публикации; stale-источник
   отображается с предупреждением, непроверенная свежесть не выдаётся за fresh.
7. Локальная сборка и превью ветки работают с относительными путями/`SITE_BASE`;
   тема, favicon, читатель и граф проверены в браузере, включая узкий экран.
8. Реальный wiki merge в одной платформе вызывает Pages `docs/main`, и сайт
   публикует ожидаемый `repositorySha`. Для двух других платформ проверены
   эквивалентный workflow/доступ и реальный ручной dispatch без искусственных
   изменений wiki. Не делать фиктивные коммиты ради запуска.
9. Проходят обязательные проверки репозиториев, где изменяются workflows/код;
   для `docs` — typecheck, tests и полная сборка. Тесты объединения используют
   локальные fixtures и не зависят от доступности GitHub или текущих wiki.

## Проверенные факты

- Установлен `openwiki@0.7.2`; `dist/visualize/static-export.js` вызывает
  `buildGraph(options.wikiRoot)` для одной wiki. Модуль объединённой визуализации
  workspace не используется и в текущем экспортном API отсутствует.
- `scripts/export-openwiki.ts` читает только `<root>/openwiki`, добавляет дату/SHA
  `docs`, favicon и пишет `dist/openwiki`. Тесты фиксируют пять native assets.
- Native client использует IDs без репозитория, относительные ссылки и общий
  reader. Его адаптация должна учитывать namespace, якоря и выбор quickstart.
- `docs/.github/workflows/pages.yml` checkout-ит только `docs`. У него есть
  `workflow_dispatch`, существующее расписание и последовательная очередь main.
- `scripts/build-site.ts` создаёт временные checkout веток и задаёт `SITE_BASE`.
  Подготовленные внешние снимки нужно явно передать в их сборку.
- README описывает workspace в `~/.openwiki`; предыдущая спека
  `2026-10-25-current-documentation-openwiki-design.md` явно ограничивала сайт
  wiki `docs`. Этот дизайн расширяет только публичную публикацию.
- На момент исследования у организации есть общий secret `ADD_TO_PROJECT_PAT`,
  но наличие и права отдельного токена публикации не подтверждены. Значения
  секретов не читались и не публиковались.
- Согласованный макет проверен в браузере: выбор фильтра и страницы работают,
  ошибок JavaScript нет; при ширине 390 px горизонтального переполнения нет.
  Это проверка макета, не реализации продукта.

## Что остаётся исполнителю

Расположение модулей, формат manifest/URL, детали адаптации клиентского кода
OpenWiki с проверками на обновление пакета, минимальные fixtures и точные
breakpoints. Публичные контракты и решения этой спеки не менять без обсуждения.
Поддержка upstream остаётся целью: пакет не редактировать в `node_modules`,
не копировать весь OpenWiki и его зависимости ради небольшого расширения.
