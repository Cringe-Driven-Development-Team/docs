# Единый маршрут к контексту проекта для агентов

## Цель

При работе в любом репозитории `Cringe-Driven-Development-Team` агент должен находить актуальный общепроектный контекст и правила своего репозитория. Архитектурное решение меняется в одном месте; локальные инструкции не становятся его копиями. Агент различает работающий прод, запланированный модуль и фактическое состояние исходников.

## Проверенные факты

- В [`docs/README.md`](https://github.com/Cringe-Driven-Development-Team/docs/blob/8ce546cacaff6d57aa6d00d55666ea69eb90bd55/README.md) рабочим назван MVP с одной VPS; `diagrams/frozen-k3s/` заморожен, а `diagrams/modules/2/` описывает план, не прод.
- [`docs/AGENTS.md`](https://github.com/Cringe-Driven-Development-Team/docs/blob/8ce546cacaff6d57aa6d00d55666ea69eb90bd55/AGENTS.md) уже требует сверять факты о работающей системе с кодом, а утверждения на сайте подтверждать ссылкой на файл и конкретный SHA.
- [`backend/AGENTS.md`](https://github.com/Cringe-Driven-Development-Team/backend/blob/d5588c7360dd431d89a714b75d1787b9e24fb084/AGENTS.md) содержит и локальные правила Go-сервиса, и пересказ общей архитектуры. В старом локальном клоне он ещё описывает две VPS, тогда как текущий `main` — одну; поэтому локальная копия другого репозитория без проверки SHA недостаточна.
- В [`frontend`](https://github.com/Cringe-Driven-Development-Team/frontend/tree/75e0ac7510c2ec4f888f84966ad7c004efbe4c6c) в корне есть `CLAUDE.md`, но нет `AGENTS.md`; в [`infra`](https://github.com/Cringe-Driven-Development-Team/infra/tree/7780b80480e97e98e548ce2380c14e2a68b2daa0) нет ни одного. У `docs`, `backend` и `frontend-packages` есть `AGENTS.md` и `CLAUDE.md`.
- [`docs/skills-placement.md`](https://github.com/Cringe-Driven-Development-Team/docs/blob/8ce546cacaff6d57aa6d00d55666ea69eb90bd55/docs/skills-placement.md) уже определяет: правила репозитория — в корневом `AGENTS.md`, `CLAUDE.md` подключает его через `@AGENTS.md`; общие скиллы — в `agent-plugins`.
- Правила задач и PR находятся в [`.github/CONTRIBUTING.md`](https://github.com/Cringe-Driven-Development-Team/.github/blob/main/CONTRIBUTING.md), а `cdd-tasks` ссылается на них как на первоисточник.

## Распределение ответственности

| Вопрос | Владелец сведений |
| --- | --- |
| Общая архитектура, границы компонентов, связи репозиториев и состояние работающего продукта | `docs`: текущие разделы сайта и схемы корня |
| Согласованное будущее изменение | `docs/site/modules/` и утверждённые проектные документы; оно явно помечено как план |
| Фактическое поведение и конфигурация компонента | исходники и конфигурация соответствующего репозитория на проверенном SHA; для состояния продакшена — ещё и проверка стенда |
| Контракт HTTP API | Apidog; локальные выгрузки и генерация проверяются по нему |
| Задачи, PR и процесс | `.github/CONTRIBUTING.md` |
| Команды, ограничения и соглашения конкретного репозитория | его `AGENTS.md`, `README.md` и локальные исходники |

`docs` становится единым местом **общепроектного контекста**, но не объявляется источником любого факта. Документация о проде должна ссылаться на подтверждающий код; при расхождении с кодом агент сообщает о нём и исправляет документацию в рамках согласованной работы. Нельзя незаметно принять план модуля за реализованное поведение.

## Как агент получает контекст

1. В репозитории агент читает его корневой `AGENTS.md`. Для Claude `CLAUDE.md` подключает тот же файл через `@AGENTS.md` и хранит только особенности Claude Code.
2. В каждом `AGENTS.md` есть короткий одинаковый указатель на входную страницу `docs` с правилом различать текущую архитектуру, планы и код. Подробности реализации и проверки остаются локальными.
3. Перед решением, влияющим на другие репозитории или архитектуру, агент открывает соответствующий раздел `docs` и сверяет относящиеся к задаче утверждения с исходниками нужных репозиториев. Для локальной правки без таких последствий ему достаточно указателя и локальных правил.
4. Скиллы остаются процедурами для отдельных задач (`cdd-tasks`, Pulumi, Ansible и т. п.). Общая архитектура и её пересказ в скиллы не копируются. Отдельный `cdd-project` сейчас не нужен.

## Изменения

1. В `docs` добавить компактную страницу или раздел «Где искать актуальные сведения» с таблицей владельцев и ссылками на текущую архитектуру, планы модулей, репозитории и правила задач. Это навигатор, без повторного описания архитектуры. Связать его с README и меню сайта, чтобы он был доступен человеку и агенту.
2. В `backend/AGENTS.md` убрать общий пересказ топологии и заменить ссылкой на `docs`, сохранив локальные Go-команды, правила API, развёртывания и проверки. Факты, которые нужны как ограничения конкретного сервиса, остаются, но должны ссылаться на код или `docs`.
3. В `frontend` перенести общие инструкции из корневого `CLAUDE.md` в `AGENTS.md`; оставить в `CLAUDE.md` подключение `@AGENTS.md` и только особенности Claude. Сохранить существующие локальные требования и команды.
4. В `infra` добавить `AGENTS.md` с указателем на `docs` и локальные README/RUNBOOK; `CLAUDE.md` нужен только если в репозитории используются дополнительные Claude-инструкции.
5. Остальные репозитории организации снабдить коротким `AGENTS.md` с тем же маршрутом к `docs` и ссылкой на свой README. Существующие локальные правила (`frontend-packages`, `docs`) сохраняются. Для Claude там, где он используется, `CLAUDE.md` подключает `@AGENTS.md`; не требуется плодить пустой файл ради формального единообразия.
6. `cdd-tasks` не менять: он уже указывает на `.github/CONTRIBUTING.md` и активируется для задач/PR, а не для каждой работы с кодом.

## Обновление и расхождения

- PR, меняющий работающую межрепозиторную архитектуру, сопровождается обновлением текущих разделов `docs` и проверкой ссылок на SHA. Если работа разбита на несколько PR, промежуточное состояние и порядок обновления фиксируются в задачах; документация не утверждает, что незавершённый план уже работает.
- PR, меняющий только локальные команды или соглашения, обновляет `AGENTS.md` своего репозитория в том же PR. Изменение общего правила поиска сведений начинается в `docs`, затем короткие указатели в репозиториях приводятся к нему.
- Если локальный клон документации или соседнего репозитория отстаёт, агент проверяет актуальный `main` перед выводом о противоречии. Несовпадение `docs`, кода и продакшена явно указывается человеку; приоритет определяется типом проверяемого факта из таблицы выше.
- Автоматическая проверка может контролировать наличие и ссылки `AGENTS.md`, но не способна доказать смысловое совпадение архитектурных описаний. Для последних нужна проверка PR.

## Порядок внедрения и приёмка

Сначала публикуется входная страница в `docs`, затем обновляются `backend`, `frontend`, `infra`, после этого остальные репозитории. PR по разным репозиториям связываются задачами по правилам `.github/CONTRIBUTING.md`; до завершения раскатки ссылка на уже опубликованный раздел `docs` действительна.

Приёмка:

- Из каждого командного репозитория агент по корневым инструкциям может попасть в `docs` и определить, где текущая архитектура, где план и где проверять фактическое поведение.
- `AGENTS.md` не содержат самостоятельного пересказа общей топологии; локальные команды и ограничения сохранены.
- Claude Code получает те же общие инструкции через `@AGENTS.md` там, где есть `CLAUDE.md`.
- Проверены ссылки и отсутствие противоречащих утверждений в изменённых файлах; локальные проверки документации и затронутых репозиториев проходят.

## Вне рамок

Не переписываем архитектуру продукта, не меняем API или деплой и не создаём новый общепроектный скилл. Содержимое замороженных схем и планов модулей этим изменением не корректируется.
