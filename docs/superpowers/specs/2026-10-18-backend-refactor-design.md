Дата исходного решения: 18.10.2026. Редакция: 19.10.2026.
Код: `Cringe-Driven-Development-Team/backend`, ветка `api-15`.
Задача: [backend#15](https://github.com/Cringe-Driven-Development-Team/backend/issues/15).
Реализация: [PR #34](https://github.com/Cringe-Driven-Development-Team/backend/pull/34).
Порядок работ и статус: [план](../plans/2026-10-18-backend-refactor.md).

## 1. Цель и согласованный результат

Разделить backend на компоненты с явной ответственностью, чтобы изменения HTTP,
хранилищ и криптографии не требовали переписывать прикладные сценарии. Результат
рефакторинга определяется направлением зависимостей и проверяемостью границ.

Domain содержит предметные типы. Usecase выполняет сценарии и объявляет нужные ему
порты. HTTP, PostgreSQL, S3 и криптографические адаптеры используют эти контракты.
App создаёт реализации и соединяет их. Точки входа в cmd остаются небольшими.

Сохраняются существующие маршруты, JSON, cookie, сроки токенов, правила авторизации
и CSRF. Единственное согласованное уточнение поведения из ревью: сбой проверки
пароля возвращает HTTP 500, а несовпадение пароля — HTTP 401. Новые ручки и новые
возможности продукта в эту задачу не входят.

Документ описывает итоговое решение для всей задачи. Большая часть рефакторинга
уже представлена в PR #34; различение ошибок пароля ещё требует реализации.
Готовность отдельных этапов отражается в плане, а требования ниже остаются
критериями приёмки независимо от текущего состояния кода.

## 3. Выбранный подход и границы компонентов

Сохраняется один Go-сервис с существующими PostgreSQL и S3. Разделение производится
внутри модуля: выделение микросервисов и замена хранилищ для этой задачи не нужны.
Порты размещаются рядом со сценариями, которые ими пользуются: именно потребитель
определяет необходимый контракт, а адаптер обеспечивает его выполнение.

| Компонент | Ответственность | Допустимые зависимости |
| --- | --- | --- |
| domain | User, Notebook, Cell и предметные типы | Стандартная библиотека; без HTTP и инфраструктуры |
| usecase | Сценарии, прикладные результаты, порты и ошибки | Domain, собственные порты и небольшие служебные зависимости |
| delivery/http | Преобразование запросов и результатов, вызов сценария | Usecase, HTTP-контракт и общие HTTP-компоненты |
| adapters | PostgreSQL, S3, ipynb, JWT, bcrypt, refresh-токены | Контракты внутренних слоёв и соответствующие библиотеки |
| transport/http | Роутер, middleware, security, cookie, ошибки | HTTP-контракты; без знания конкретных хранилищ |
| app | Создание и соединение реализаций, запуск | Config и компоненты приложения |
| tooling/apidog | Получение и проверка контракта | HTTP-клиент, окружение, файловый вывод |

DTO генератора остаются на HTTP-границе. Usecase не импортирует HTTP, адаптеры
или конкретные криптографические библиотеки. Domain не импортирует usecase.
Переданный context сохраняется при переходах от обработчика к сценарию и хранилищу.

## 5. Прикладные порты и ошибки

### 5.1. Пользователи и сессии

UserStore отвечает за пользователей, SessionStore — за refresh-сессии. Оба порта
пока реализует PostgreSQL. Разделение не меняет схему БД и семантику ротации.
Session с токенами является результатом сценария, а User остаётся типом domain.

PasswordHasher выполняет хеширование и сравнение; TokenIssuer выпускает access JWT;
RefreshTokens создаёт refresh-токен и вычисляет его хеш. Сохраняются bcrypt cost,
алгоритмы, форматы и сроки токенов. Ошибка хеширования не создаёт пользователя или
сессию; ошибка выпуска access-токена не создаёт сессию.

### 5.2. Контракт проверки пароля

Для реализации выбран предложенный ментором вариант с отдельными результатами:

```go
Hash(password string) (string, error)
Compare(hash, password string) (matched bool, err error)
```

Это технический выбор плана из двух допустимых вариантов ревью. Вариант с отдельной
ErrPasswordMismatch также обсуждался, но одновременно оба механизма не вводятся.

| Результат проверки | Результат usecase | HTTP |
| --- | --- | --- |
| true, nil | Продолжить создание сессии | Прежний успешный ответ |
| false, nil | ErrInvalidCredentials | 401 |
| false, err | Обернуть ошибку с сохранением причины | 500 |

В bcrypt-адаптере только ErrMismatchedHashAndPassword означает несовпадение.
Повреждённый или неподдерживаемый хеш — ошибка проверки. Login сначала проверяет
err, затем matched. При обоих видах отказа токены не выпускаются и сессия не создаётся.
Внутренняя причина доступна логированию, но не попадает в JSON-ответ клиенту.
Отсутствующий пользователь по-прежнему даёт ErrInvalidCredentials.

### 5.3. Блокноты

Metadata описывает операции над метаданными, Files — чтение и запись ipynb в S3,
NotebookCodec — Parse/Build. Usecase использует порт кодека вместо конкретного
адаптера ipynb. Ошибка кодирования при создании не записывает файл или метаданные.
Проверка владельца выполняется до доступа к файлу. Ошибки хранения определяются
рядом с портами и преобразуются в прикладные результаты сценариев.

Часы и генерация ID могут оставаться небольшими подменяемыми зависимостями.
Интерфейс вводится там, где нужна граница ответственности или проверка отказов.

## 6. HTTP, CSRF и cookie

| Компонент | Обязанность |
| --- | --- |
| CSRFSigner | Выпуск и проверка токена без http.Cookie |
| CSRFGuard | Проверка исходного запроса, Origin, cookie, заголовка и подписи |
| CSRFBootstrap | Выдача отсутствующей cookie и согласование её с ответом обработчика |
| SessionCookies | Создание и удаление cookie после login/refresh/logout |
| RefreshUserResolver | Чтение владельца сессии с разделением недействующей сессии и сбоя |

Resolver возвращает RefreshIdentity с UserID и Valid, а инфраструктурный сбой —
отдельной ошибкой. Адаптация ErrInvalidRefresh находится в delivery/http;
общая HTTP-защита не импортирует ошибки user/usecase.

Порядок запроса: RequestID → Logging → Recover → CORS → CSRF/Authenticate → Validator.
Общие middleware оборачивают ранние отказы, preflight, 404 и 405.
Проверка refresh/logout по владельцу сессии используется до её изменения.

Обязательные свойства:

- Восстановленная cookie не делает исходный запрос валидным.
- Повреждённая подписанная cookie не исправляется автоматически.
- Повторяющиеся CSRF-cookie и заголовки отклоняются.
- CSRF-отказ не ротирует и не удаляет refresh-сессию.
- Cookie успешного login/refresh/logout имеет приоритет над bootstrap.
- Сохраняются текущие Origin-ограничения, атрибуты cookie и реакции на сбои хранилища.

## 7. OpenAPI и воспроизводимая генерация

Apidog остаётся источником контракта. Схема cookieAuth описывает фактическую
аутентификацию: type apiKey, in cookie, name access_token. Bearer-аутентификация
не добавляется; validator отклоняет неизвестную или неверно описанную схему.

| Политика | OperationID |
| --- | --- |
| cookieAuth | GetCurrentUser, ListNotebooks, CreateNotebook, GetNotebook, CreateCell, DeleteCell |
| Публичная в OpenAPI | RegisterUser, LoginUser, RefreshToken, LogoutUser |

Публичность refresh/logout в OpenAPI не отменяет их refresh- и CSRF-проверок.
Тест перечисляет ожидаемые операции и выявляет новую неклассифицированную ручку.
Рабочий код получает политику из OpenAPI; второй независимый список маршрутов
для принятия решения об авторизации не создаётся.

Изменения Apidog проходят review в sprint-ветке и попадают в main. Генерация
выполняется из согласованного main, повторный запуск даёт тот же Go-файл.
Сгенерированное содержимое вручную не правится. При переносе сохраняется код
вне embedded spec; изменение схемы выполняется генератором.

## 8. Настройки, запуск и экспорт

Config читает окружение и проверяет обязательные JWT_SECRET, CSRF_SECRET и
S3_NOTEBOOKS_BUCKET. Сохраняются существующие значения по умолчанию, fallback
для неверной длительности и экранирование PostgreSQL URL.

App соединяет адаптеры, usecase и HTTP, затем запускает сервер с прежней моделью
освобождения ресурсов. Новая модель остановки сервера не входит в задачу.

Cmd/apidog разбирает CLI и завершает процесс; tooling/apidog выполняет экспорт,
проверяет ответ и записывает файл. HTTPClient, LookupEnv и Log подменяются в тестах.
Сохраняются параметры CLI, приоритет окружения над env-файлом и команды Makefile.
Ошибки авторизации, конфигурации или формата ответа не оставляют успешный выходной файл.

## 9. Приёмка

| Требование | Подтверждение |
| --- | --- |
| Направление зависимостей | go list и depguard: domain/usecase без HTTP, адаптеров и crypto |
| Отказы прикладных портов | Тесты ошибок hasher, token issuer и codec без побочных записей |
| Различение ошибки пароля | Адаптер + Login + HTTP: несовпадение 401, сбой 500, причина сохранена, сессии нет |
| Сохранение HTTP/CSRF | Существующие сценарии, bootstrap, Origin, cookie и ранние ответы |
| Конфигурация и экспорт | Defaults/overrides, обязательные настройки, URL, ошибки и подменённый HTTP |
| Контракт авторизации | Классификация операций, отказ неизвестной схемы, повторная генерация |
| Качество и сборка | make check, make docker-build, git diff --check |
| Документация | Актуальные пути в README/AGENTS.md; AGENTS.md не более 150 строк |

Успешная общая сборка не заменяет проверки поведения 401/500. Задача готова к
повторному ревью после выполнения всех критериев, включая замечание ментора.

## 10. Не входит

Redis и атомарная ротация сессий (задача #17), новые ручки, миграции БД,
production-инфраструктура, BFF, новая SQL/XSS-политика и расширение логирования.
Задачи #13, #14, #17–#23 не реализуются попутно. Существующие подмены тестов
адаптируются без перехода на gomock/sqlmock. Проблемы согласованности S3/БД
и прежняя семантика ротации сохраняются в границах этой задачи.

Личные настройки не включаются в проектные изменения. Командные настройки
сохраняются. Коммиты, push и публикацию PR выполняет автор изменений.
