# Раздел front-libs: монорепозиторий, релизы и Trusted Publishing

Дата: 2026-10-17. Репозиторий: `Cringe-Driven-Development-Team/docs`.

## Цель и согласованный результат

Развернуть существующий трек `/modules/2/tracks/front-libs` в практическое объяснение
переезда фронтовых библиотек в монорепозиторий. Читатель должен понимать, чем подготовка
версий через release-please отличается от авторизации публикации, как сравниваются
публикация с npm-токеном и Trusted Publishing, как проходит каскадный релиз и что
нужно проверить до обновления проекта-потребителя.

Сохраняем существующий адрес и одну страницу. Альтернатива с отдельными подстраницами
отклонена на этом этапе: материал последовательно читается в одном месте.

Раздел описывает план внедрения для CDD. Работающий пример `TP-Prepare/frontend-packages`
обозначается отдельно и подтверждает выбранный подход. Реализация монорепозитория CDD
в эту работу не входит.

Пользователь также поручил актуализировать ТЗ
https://github.com/Cringe-Driven-Development-Team/frontend/issues/18 при необходимости.
Обновляется только описание задачи; статус, спринт, исполнитель, название и связи задач
сохраняются. Основа новой редакции приведена ниже и входит в предмет проверки спецификации.

## Содержание страницы

### Что переносим и зачем

Кратко описать три учебные библиотеки, текущие и целевые npm-имена и пользу общего
workspace: единый тулинг, общий CI, локальная проверка связки React и Zustand.
Явно сказать, что речь об учебных реализациях команды, а не об автоматическом
обновлении upstream React и Zustand в разных репозиториях.

Разделить две задачи: release-please подготавливает версии, CHANGELOG и release PR;
выбор npm token / OIDC определяет, как CI получает право отправить архив в npm.
Оба способа авторизации могут использовать один и тот же процесс подготовки релиза.

### Сравнение способов публикации

Старый способ описать как token-based подход, а не как доказанный факт о прежнем CI
CDD: сейчас в исходных библиотеках подтверждена ручная публикация.

Показать цепочку `npm token → GitHub Secrets NPM_TOKEN → env NODE_AUTH_TOKEN → npm publish`.
Уточнить, что секрет хранится в GitHub Secrets и передаётся в env только нужного job;
не предлагать сохранять токен открытым текстом в обычной repository variable.
Не советовать создавать устаревшие classic/automation tokens; для контекста сослаться
на актуальные правила granular tokens и их ограничений.

Показать цепочку `запуск GitHub Actions → OIDC identity → проверка npm Trusted Publisher
→ короткоживущие права → npm publish`. Раскрыть `id-token: write`, настройку каждого
пакета, точный workflow filename и действие Allow npm publish. Объяснить,
что постоянный npm-секрет в репозитории не нужен; GitHub-доступ release-please
к PR и GitHub Releases остаётся отдельным механизмом.

Таблица сравнения: источник полномочий, хранение npm-секрета, срок полномочий,
отзыв и обслуживание, настройка для пакета/workflow, ограничения по runner/CLI.
OIDC проверяет идентичность workflow и не заменяет проверки кода и права на изменение workflow.

Примеры YAML — компактные фрагменты job публикации с явно указанным контекстом.
Выражения GitHub Actions размещаются в fenced code blocks, чтобы VitePress не
интерпретировал их как Vue. Для CDD рекомендуем Trusted Publishing.

### Цикл релиза и независимые версии

Последовательность: изменение пакета → CI PR → merge в main → release-please
создаёт release PR → проверки и merge release PR → отдельные теги/GitHub Releases
→ сборка и публикация только выпущенных пакетов в порядке зависимостей.
Публикация и появление версии в доступных npm-метаданных могут разделяться задержкой;
итог проверяется через `npm view` и установку, а не только по созданному GitHub Release.

У пакетов независимые версии. Для связи `@cdd-team/zustand → @cdd-team/react`
задать `node-workspace` и `updatePeerDependencies: true`, публичный peer semver
и локальную dev-связь workspace; optional peer и экспорт vanilla сохраняются.

Пример после начальной публикации: исправление только в React `1.2.0 → 1.2.1`
вызывает `zustand 1.0.0 → 1.0.1` и обновление peer-диапазона до `^1.2.1`;
`openapi@0.2.0` остаётся прежним. Исправление только в Zustand выпускает только Zustand.
Коммиты распределяются по изменённым путям, scope сам по себе не выбирает пакет.

### Проверка совместимости

До публикации CI собирает и тестирует пакеты с актуальными локальными workspace-
зависимостями. Нужны интеграционные тесты React/Zustand и проверка опубликованной
формы пакетов через установку архивов в отдельный проект.

Разделить сборку, проверку типов и runtime-тесты: успешная сборка не доказывает
работу хуков и обновлений состояния. Автоматическое изменение peer-диапазона
не подтверждает совместимость с breaking-версией. Проверки потребителя сохраняются:
его собственные сценарии могут отсутствовать в тестах библиотек.

### Первоначальная настройка и проверка результата

Список настроек: npm-организация `cdd-team` и права участников, имена пакетов,
метаданные repository, начальные версии, разовая публикация и соответствующие
GitHub Release-теги как точки отсчёта, Trusted Publisher на каждом пакете.
Для GitHub — owner `Cringe-Driven-Development-Team`, repo `frontend-packages`,
workflow filename `release.yml`, environment только если он используется.

Bun остаётся инструментом установки, тулинга, тестов и сборки. npm CLI и подходящая
версия Node используются в job публикации для документированного OIDC-процесса;
переход сборки и основных проверок с Bun на npm в задачу не входит.

Показать проверяемые сценарии: patch только Zustand; patch React с каскадом;
нерелизный docs/test без breaking change; установка выпущенной связки.
Описать восстановление после ошибки: узнать реально опубликованные версии,
не пытаться повторно записать существующий name/version, отдельно завершить
отсутствующую публикацию. Начальная ручная регистрация — разовая операция,
обычные релизы идут через workflow.

## Три схемы

Схемы реализуются по `.agents/skills/eraser-diagrams/SKILL.md`, JSON с абсолютными
координатами по сетке 20, короткими читаемыми подписями и одной легендой справа.

1. `front-libs-npm-token`: рабочее место владельца (white), GitHub (purple), npm (green).
   Узлы: владелец, создание токена, GitHub Secrets, job публикации, npm registry.
   Связи показывают регистрацию секрета, передачу в env и авторизованную загрузку архива.
   Значение самого токена нигде не изображается.
2. `front-libs-trusted-publishing`: GitHub (purple), npm (green).
   Узлы: job с `id-token: write`, OIDC GitHub, настроенный Trusted Publisher,
   выдача краткоживущих прав, публикация архива. Подписи явно отличают
   идентичность GitHub от npm-полномочий и показывают проверку repo/workflow.
3. `front-libs-release`: GitHub (purple), npm (green); проект-потребитель как
   подписанный нейтральный узел. Этапы PR и CI, release-please, общий release PR
   с независимыми версиями, GitHub Releases и последовательная публикация
   React → Zustand. Рядом с CI — проверка связки локальных пакетов;
   сбой останавливает прохождение этого этапа. Обновление потребителя следует
   за публикацией. OpenAPI показывается как независимый пакет без каскадного выпуска.

Каждая схема встраивается через `<Diagram name="modules/2/front-libs-…" />`
возле соответствующего объяснения. PNG проверяются глазами после рендера;
легенда и цвета проверяются существующим скриптом.

## Границы

Не переносить код библиотек и их git-историю в этой работе, не менять их версии,
не настраивать npm-аккаунты, не публиковать пакеты и не отзывать токены.
Не менять существующие завершённые треки, корневые схемы продакшена,
доску, статусы задач и участников. Глобальная установка или правка навыков
не требуется: используются актуальные навыки из репозитория `docs`.
