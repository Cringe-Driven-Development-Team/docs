# Актуальная архитектура работающего сервиса

Статус: принята к реализации; владелец выбрал `superpowers:executing-plans` 01.11.2026.
Дата: 01.11.2026. Репозиторий реализации: `Cringe-Driven-Development-Team/docs`.

## Зачем

Раздел `/architecture/` пока показывает схемы MVP до BFF и ссылки на замороженный
k3s. Страница предупреждает об историческом состоянии, но не даёт целостной картины
работающего сервиса. После переноса Go, PostgreSQL и Redis на VPS2 эта картина уже
подтверждена непосредственно на серверах.

Студент и его агент должны по разделу понять, где работают компоненты, кто ими
владеет, как проходят запросы и как выпускаются изменения. Раздел описывает
наблюдаемое размещение и подтверждённые механизмы; наличие кода или успешная сборка
не превращает непроверенный пользовательский сценарий в работающую возможность.

## Решения и подходы

Предложение автора этой спеки — обновить существующие шесть корневых схем на месте.
Это сохраняет знакомую структуру и разделяет размещение, frontend, контракт и выпуск.
Рендерер eraser-diagrams и компонент `Diagram` уже решают задачу отображения.

Рассмотрены три подхода:

1. **Обновить шесть схем и пояснения — предложен.** Сохраняются имена и адреса,
   каждая схема отвечает на отдельный вопрос. Нужна согласованная проверка всех шести.
2. **Заменить их одной общей схемой.** Меньше файлов, но размещение, кодогенерация,
   очереди CI/CD и служебные интеграции перегружают один рисунок. Для текущей задачи
   потеря читаемости важнее сокращения числа файлов.
3. **Перестроить раздел в новый многостраничный каталог.** Уместно при росте материала,
   сейчас добавляет навигацию и переносы без необходимости для актуализации фактов.

Удаление k3s и актуализация по проду запрошены владельцем. Сохранение шести схем,
их порядок, состав пояснений и сопоставление старых URL ниже — решения автора,
предлагаемые к утверждению вместе с документом. Новая система диаграмм не нужна.

## Область изменения

1. Переписать `site/architecture/index.md`, заменив историческую модель текущим срезом.
2. Обновить шесть JSON в корне `diagrams/`: `deployment`, `ci`, `cd`, `frontend`,
   `contract`, `infra`.
3. Удалить пять JSON из `diagrams/frozen-k3s/` и их активные ссылки; старые HTML-адреса
   направить на актуальные схемы штатным механизмом переадресаций.
4. Согласовать README, подпись пункта sidebar и инструкции о размещении схем.
5. Обновить существующие проверки раздела, списков и переадресаций.

Работа ограничена репозиторием `docs`. Модули сохраняют планы и историю. Изменения
серверов, контрактов, приложения, cloud security groups, backup jobs и backend release
документации оформляются отдельной работой; аудит не даёт разрешения их менять.

## Страница архитектуры

Заголовок: «Архитектура работающего сервиса». Существующий явный ID
`архитектура-mvp` оставить для входящих ссылок; он не определяет содержание страницы.

Сверху до шести разделов разместить:

- короткое назначение раздела и дату проверенного среза;
- компактную таблицу размещения: gateway, VPS2, auxiliary, внешние S3/CDN/GitHub;
- свидетельство проверки: дата, backend SHA, BFF revision/digest, ссылка на успешную
  выкладку Go и наблюдаемые HTTP-ответы; SHA кода и факт выкладки различаются явно;
- границу проверки: авторизованные сценарии и runtime-сессии не подтверждены;
- ссылки на каноническое описание BFF и текущий контекст/владельцев.

Шесть разделов оставить в текущем порядке: `deployment`, `ci`, `cd`, `frontend`,
`contract`, `infra`. Имена `##`, якоря и `<Diagram name="…" />` сохраняются.
Дополнительные блоки вводной части оформить без новых заголовков `##`, чтобы
сохранить понятный список схем. В каждом разделе — вопрос, который решает схема,
короткое пояснение границ и ссылки на источники реализации на конкретных SHA.
Полные отчёты CI и runbook на эту страницу не переносить.

В sidebar заменить «Архитектура и исторические схемы» на «Архитектура».
В `site/documentation/index.md` заменить описание ссылки, которое сейчас говорит
о сохранённых исторических схемах MVP. Старые датированные проверки BFF/CSRF не
переписывать в свежие и не объявлять расширенными этой работой.

## Содержание шести схем

| Схема | Основной вопрос | Обязательное содержание |
| --- | --- | --- |
| `deployment` | Где работает сервис и как идёт запрос? | Браузер → Caddy/BFF на gateway → Go на приватной VPS2 → PostgreSQL/Redis; релизные JS/CSS через S3/CDN; S3 продуктовых данных с пометкой уровня проверки; auxiliary отдельной группой, не частью каждого пользовательского запроса |
| `ci` | Кто что проверяет и публикует? | Командные frontend/backend/infra/docs; проверки отдельно от публикации и deploy; GHCR, S3 release assets; синхронизация frontend/backend в учебные копии как односторонняя публикация; `frontend-packages` → npm/OIDC и `static` → свой S3/CDN как соседние владельцы |
| `cd` | Как выпуск становится работающим релизом? | Frontend: ручной выбор выпуска, BFF digest и связанные ассеты, Ansible, проверка результата; rollback выбирает существующий выпуск. Backend: main → CI/image → автоматический Ansible CD → VPS2 через gateway → health. Миграции PostgreSQL относятся к Go; откат BFF не откатывает БД. Infra: Pulumi/Ansible, отдельно от выпуска frontend/backend |
| `frontend` | Где менять frontend и его зависимости? | `apps/client`, `apps/bff`, схемы; командные React/router/zustand; browser ↔ BFF через tRPC, BFF → Go через сгенерированный HTTP-клиент; HTML/bootstrap, серверная работа с сессией, CDN ассетов. `frontend-packages` владеет общими библиотеками и Vite plugin, frontend их потребляет |
| `contract` | Какие контракты связывают стороны? | Apidog/OpenAPI → Go/oapi-codegen и BFF/Orval/Zod; browser ↔ BFF через tRPC; механизм проверки drift по фактическим workflow. Генерация и потребление схем не равны выкладке. Не добавлять отсутствующий frontend drift workflow |
| `infra` | Кто управляет инфраструктурой и служебными потоками? | Три постоянные VPS и их роли; Selectel/Pulumi с отделённым backend состояния; Ansible; S3/CDN; auxiliary hooks → очередь/Telegram proxy → Telegram, backup auxiliary. Runtime от Go выделен как «включён, пользовательский сценарий не проверен»; не рисовать успешную созданную runtime-VPS как наблюдавшийся факт. Docs/Pages/OpenWiki — отдельный поток публикации знаний |

Одна связь на схеме — один подтверждённый механизм. Вызовы Go → S3, BFF → Go и
runtime-провайдер показывают настроенную архитектурную связь; пояснение рядом
указывает, какой сценарий реально проверен. Проверка `/health` не доказывает login,
доступ к блокнотам, сохранность данных или выполнение Python/R.

Убрать утверждения текущей модели о k3s/Argo CD/Coolify/канарейке, TanStack Router,
`@my/openapi`, прямом браузерном `/api/v1`, раздаче HTML из S3 через `current.json`
и обязательной совместимости клиента N с Go N+1. Если подобные имена встречаются
в планах модулей или исторических спеках, это не повод править историю.

## Отображение, источники и ограничения

Сохраняются текущий eraser renderer, zoom/pan, HTML/PNG, тема и существующие цвета
зон владения. Формат, легенда, сетка и цикл validate → check → render → осмотр PNG
следуют `.agents/skills/eraser-diagrams/SKILL.md`. Никаких новых зависимостей.

Не выводить реальные IP, CIDR, приватные URL, секреты и полные конфиги. Узлы
называть ролями (`gateway`, `VPS2`, `auxiliary`); приватное соединение обозначать
как приватную сеть, не раскрывая её адреса. Допустимы публичные домены и GitHub-ссылки.

В свойствах текста/подписях не вводить несуществующие сервисы или гарантии высокой
доступности. Отдельно указать, что восстановление продукта из backup не проверено;
backup auxiliary не объявлять backup PostgreSQL на VPS2. Остальные замечания
аудита не превращаются в новые требования к реализации этой задачи.

OpenWiki остаётся производным указателем. Исполнитель не обновляет её автоматически
и не правит generated Markdown руками. После отдельного ручного обновления владельцем
wiki опирается на изменённые канонические документы; до этого пометка stale допустима.

## Приёмка

1. `/architecture/` показывает дату и свидетельство среза, три роли VPS и все шесть
   актуальных схем. Go/БД/Redis размещены на VPS2; на gateway Caddy/BFF.
2. Утверждения о коде и стрелки имеют подтверждение в исходниках на полном SHA;
   на странице различаются наблюдение на проде, конфигурация и непроверенный сценарий.
   `RUNTIME_ENABLED=true` не преподносится как проверенное выполнение кода пользователя.
3. Состав и адреса корневых схем, шесть якорей и старый явный ID страницы сохраняются.
   Не осталось активного описания архитектуры до BFF или ссылок на Frozen в текущем разделе.
4. Пять k3s JSON удалены; все пять HTML-переадресаций ведут на существующие корневые
   схемы. Старые hash-входы работают на основном сайте и под базой превью ветки.
   Чистая сборка не содержит рендеров старых k3s-схем.
5. Существующие тесты обновлены под новые факты и поведение ссылок. Проверяются
   направления переадресаций, отсутствие Frozen JSON, согласованность шести схем,
   таблицы размещения и границы runtime. Тесты не фиксируют декоративные фразы
   или полный JSON координат; неизменные PNG fixture-тесты не переписываются без причины.
6. При реализации проходят `bun run modules:check`, `bun run validate`, `bun run check`,
   `bun run typecheck`, `bun run test`, `bun run wiki:prepare`, `bun run build`.
   `build` включает проверку ссылок/якорей `site:check`; схемы отдельно осмотрены по PNG.
7. В собранной странице и превью проверены шесть `Diagram`, читаемость подписей/легенд,
   работа zoom/pan, тёмная/светлая темы и отсутствие горизонтального переполнения
   страницы на мобильной ширине. Пять удалённых HTML-адресов и hash-входы проверены
   переходами, а не только сравнением строк в тесте.
8. После разрешённого слияния проверены Pages и `/architecture/` на публичном домене.
   Готовность страницы не выдаётся за повторный функциональный аудит всего продукта.
