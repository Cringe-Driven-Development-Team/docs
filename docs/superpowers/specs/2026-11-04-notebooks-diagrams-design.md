# Схемы редактора и исполнения блокнотов

Статус: согласовано пользователем 04.11.2026. Дополнение к документации в PR [docs#146](https://github.com/Cringe-Driven-Development-Team/docs/pull/146), ветка `docs/notebooks-track`.

## Цель и принятый объём

Студент должен понимать, где заканчивается его задача, как сохранение связано с запуском и откуда приходят результаты. Добавить три схемы к существующим объяснениям: обзор компонентов, сохранение с конфликтом, исполнение с получением результатов. Пользователь согласился с предложенным набором и попросил сразу перейти к спеке, без браузерного черновика.

Глубина обзора — решение исполнителя: показать Go, provisioning, runtime-агента, kernel и постоянное хранение; создание VPS свернуть до одного действия. Не раскрывать сеть OpenStack, установку пакетов, порты, секреты и алгоритм восстановления облачных ресурсов. Это сохраняет понятную связь с backend#13, не превращая страницу блокнотов в руководство по инфраструктуре.

## Подходы

- **Одна схема Eraser и две последовательности Mermaid — предложенный и принятый вариант.** Соответствует уже используемому оформлению трека 2FA: обзор показывает компоненты и границы ответственности, последовательности — порядок запросов и развилки.
- **Все три схемы в Mermaid.** Проще единый формат исходников, но обзор компонентов будет отличаться от архитектурных схем проекта. Не выбран.
- **Одна общая схема всех операций.** Меньше файлов, но смешиваются размещение, сохранение, конфликты и исполнение; такую схему трудно читать на странице и телефоне. Не выбран.

## 1. Компоненты и ответственность

**Где:** `file-exec.md`, рядом с картой работ. **Формат:** Eraser, `diagrams/modules/2/notebooks-components.json`.

Логическая схема взаимодействия, не полный маршрут сетевых пакетов. Узлы и связи:

| Откуда | Куда | Смысл |
| --- | --- | --- |
| Браузер | BFF | `notebooks.get`, `cells.*`, `runtime.*` через tRPC |
| BFF | Go API | Чтение и мутации блокнота, команды runtime; агрегация ответа экрана |
| Go API | PostgreSQL | Метаданные/ссылка на редакцию; целевые сессии, исполнения, события и курсоры |
| Go API | S3 | ipynb с исходниками и сохранёнными outputs |
| Модуль сессий Go | EnvironmentService внутри того же Go | `RequestCreate / Get / RequestDelete` |
| Provisioning | Selectel API / runtime-VPS | Создание, настройка и удаление окружения, один укрупнённый процесс |
| Модуль сессий Go | Runtime-агент на VPS сессии | Команды и получение событий/результатов по защищённому API |
| Runtime-агент | Jupyter/kernel в Docker | Выполнение кода в пользовательском окружении |

На стороне браузера подпись различает: #37 — редактор/сохранение; #38 — подсветка/Markdown поверх него; #51 — управление исполнением. Не рисовать для #38 отдельный редактор, API или путь сохранения.

На схеме явно видны граница Go backend и граница runtime-VPS с вложенным контейнером kernel. EnvironmentService — внутренний модуль, не новый сервис. BFF не создаёт VPS; агент не пишет ipynb непосредственно в S3 и не общается с браузером. Результаты сохраняет Go; они остаются доступны после удаления VPS. Сетевые прокси, не влияющие на эти обязанности, в логический обзор не включаются.

## 2. Сохранение и конфликт

**Где:** `file-exec/contract.md`, раздел «Сохранение и конфликты». **Формат:** Mermaid sequenceDiagram. Участники: редактор (#37), BFF, Go API.

Основной пример — изменение source существующей ячейки:

1. Ввод меняет локальный черновик. Через 500 мс без ввода либо при flush на blur/запуск готовится сохранение; незавершённую IME-композицию не отправляют.
2. Общая очередь блокнота отправляет `cells.update` с последним подтверждённым hash; BFF вызывает PATCH с `If-Match`.
3. **Успех:** Go возвращает `{hash, cell}`; редактор обновляет подтверждённый снимок и hash. Более новый ввод остаётся черновиком и не затирается старым ответом; следующий запрос берёт новый hash.
4. **409:** очередь со старым hash останавливается, локальный текст сохраняется. `notebooks.get` получает серверную версию; продолжение записи требует явного решения пользователя после сравнения.

В диаграмме — развилка успех/409. Рядом короткое обязательное пояснение: при сети/500 результат записи может быть неизвестен, поэтому перед повтором нужна сверка; автоматического повтора мутации со свежим hash нет. «Сохранено» допустимо лишь после подтверждения актуальной правки. Другие мутации перечисляются в тексте как использующие ту же очередь, без четырёх копий диаграммы.

## 3. Исполнение и результаты

**Где:** `file-exec/contract.md`, рядом с разделами «Перед запуском» и «Результаты и очередь». **Формат:** Mermaid sequenceDiagram. Участники: UI исполнения (#51), общий редактор (#37), BFF, Go API, runtime-агент.

Предусловие: runtime уже READY. Его создание показано в обзорной схеме; последовательность начинается с нажатия запуска.

1. #51 ждёт подтверждения сохранения выбранного кода и структурных операций через общий интерфейс #37. Ошибка/конфликт завершает этот путь без исполнения. Новые правки во время ожидания не разрешают молча исполнить устаревшую версию; требуется новый пользовательский запуск согласно #51.
2. #51 отправляет `runtime.execute` для сохранённого source, `cell_id` и отдельного `source_hash`. Go фиксирует идентификатор исполнения до передачи команды агенту. Hash блокнота и source_hash не смешиваются.
3. Агент принимает команду, ставит её в очередь/исполняет, отдаёт события и результаты Go. Ответ о принятии не изображать завершением исполнения. Не предписывать новый способ транспорта Go ↔ агент: подпись «получение событий» без обещания браузерного WebSocket.
4. Независимый цикл Go сохраняет полученные события и результат исполнения, проверяет соответствие актуальной ячейке и применяет outputs при совпадении. Поздний результат изменённого source остаётся в истории исполнения; это не ошибка самого kernel и не повод запускать код повторно.
5. Цикл браузера вызывает `runtime.updates`; BFF агрегирует состояние сессии, очередь, события и результаты конкретных исполнений. UI применяет снимки результатов без перечитывания всего content ради каждого вывода. Опрос браузера не запускает исполнение и не продлевает активность.

Последовательность должна визуально различать обработку событий Go и polling браузера: сохранение outputs не зависит от наличия открытой вкладки. Удалённое из очереди исполнение не считается потерянным — результаты доступны по execution_id. `output_truncated` сохраняется с outputs для повторного открытия блокнота.

Массовый запуск — короткая заметка рядом: один `runtime.executeAll` фиксирует набор/порядок code-ячеек по правилам #51, затем использует тот же путь отслеживания. Не рисовать массовый запуск как последовательность независимых команд браузера на каждую ячейку.

## Размещение и визуальные требования

- Все три изображения помечены как целевая модель второго модуля. Наличие кода provisioning/агента не доказывает готовность всей цепочки или выкладку.
- Обзор — на общей странице; последовательности — в существующей общей подстранице. Из редактора остаётся ссылка туда, без дубликатов схем и новых страниц.
- Использовать существующий `DiagramSection`: пояснение рядом на широком экране, над схемой на узком. Сохраняются заголовки и опубликованные якоря.
- Подписи по-русски, имена процедур/полей — как в контракте. Подробные условия остаются читаемым текстом рядом, а не мелким шрифтом внутри картинки.
- Соблюсти цвета/легенду Eraser и тему Mermaid проекта. Не добавлять свои виджеты зума, плагины и зависимости. Логические области браузера, Go и runtime нельзя спутать с отдельными микросервисами.
- У последовательности исполнения видимая пометка со ссылкой на «Статус хэша»: отсутствие перечитывания content ради нового hash после outputs относится к целевой семантике, пока опубликованный контракт расходится с ней.

## Изменяемые файлы и проверка

Создать JSON обзорной схемы; изменить только `file-exec.md`, `file-exec/contract.md`, соответствующую строку таблицы схем в README и необходимые проверки страниц. Схемы остаются в `diagrams/modules/2`; для нового файла проверить существующий HIDDEN_FOLDERS, не переносить его в раздел архитектуры прода и ROOT_NAMES.

Проверить семантику стрелок по источникам; Eraser — validate → check → render → осмотр PNG; Mermaid — синтаксис и фактический рендер в VitePress. В браузере проверить обе темы, desktop и 360 px, чтение подписи, отсутствие наложений/обрезки, зум и обычную прокрутку страницы. Проверить переход к «Статусу хэша» и старые якоря. Затем modules:check, typecheck, тесты и сборка по правилам репозитория; обновить PR и проверить превью.

Спека не меняет API, задачи, назначения или архитектуру runtime. После согласования — отдельный план реализации и выбор способа его выполнения по правилам сессии.
