# OpenWiki для общепроектного контекста CDD — дизайн

## Назначение

Дать агентам в `docs`, `frontend`, `backend` и `infra` быстрый путь к общепроектным сведениям, а людям — связанные тематические страницы. Канонический текст остаётся в `docs` и меняется через Git/PR. Wiki — созданное OpenWiki представление этого текста; найденный факт перед использованием сверяют с исходным документом, а факт о реализации — с кодом компонента на актуальном SHA. Исправление начинают с источника, после чего обновляют wiki.

В `docs` CI собирает сайт на PR, Pages публикует `main` и превью веток.

## Границы и принципы

- Не удалять `docs` и не переносить редактирование первичного текста в wiki.
- Не выдавать страницы модулей и старые спеки/планы за реализованное поведение. Разделы сайта вне модулей описывают текущий продукт, но утверждения о коде всё равно требуют проверки на SHA.
- Не включать в wiki секреты, реальные IP/CIDR и внутренние адреса. Доступ к модели остаётся в локальной авторизации Codex; GitHub Actions не получает ключ модели.
- Не добавлять поддержку старого API/клиента, поэтапное переключение и требования высокого uptime. К преподавательской проверке опубликованные сведения и продукт должны быть рабочими.
- Изменение поведения `frontend`, `backend` и `infra` не входит в эту миграцию. Их `AGENTS.md` получают только короткую навигацию к общему индексу.

## Устройство

1. В `docs/openwiki/` хранится сгенерированная `code` wiki: страницы, индексы, `.claims/`, `.page-manifest.json`, `.last-update.json`; временный `.run.json` не коммитится. `docs/openwiki/INSTRUCTIONS.md` — написанная человеком цель генерации: корпус `README.md`, `AGENTS.md`, `CLAUDE.md`, `site/`, `docs/superpowers/` и относящиеся к ним схемы/скрипты; модули и старые планы маркировать как планы; писать по-русски; в тематических страницах давать путь к источнику. `.openwikiignore` исключает копии скиллов, сборочные файлы и служебные данные.
2. Wiki доступна человеку через GitHub Markdown: ссылка на `openwiki/quickstart.md` в `site/project-context.md` и README `docs`. Относительные ссылки между страницами сохраняются. Этот вариант использует уже существующий хостинг GitHub и не добавляет второй сайт. Исходные пути `repo://` в frontmatter/Claims раскрываются в ссылку на `docs/blob/<зафиксированный SHA>/<путь>#L...` в указателе для читателя или при ответе агента; один лишь `repo://` не является проверкой факта.
3. Агенту в каждом из четырёх репозиториев `AGENTS.md` указывает на wiki в `docs`. При наличии соседнего актуального клона и MCP он использует `openwiki_search`/`openwiki_read` с корнем `docs`; без MCP — читает `openwiki/quickstart.md` и целевые страницы. Wiki запрашивается при конкретном вопросе или неясности, не загружается целиком при старте каждой задачи. Перед доверием к wiki агент проверяет свежесть клона и исходников. Если wiki устарела, её можно использовать как указатель путей, но каждое нужное утверждение проверяют по каноническому документу на актуальном SHA; если wiki недоступна или путь исчез, ищут напрямую в `docs`.
4. Перед первой генерацией блок OpenWiki в `docs/AGENTS.md` и указатель `CLAUDE.md` фиксируются отдельным исходным коммитом. **Обновление запускается только по явной команде владельца**: локальный `codex exec` с авторизованной подпиской и установленной интеграцией OpenWiki проводит `init`/`update` по её MCP lifecycle в отдельном worktree. Модель не запускается в GitHub Actions и API-ключ не требуется. Локальная команда проверяет wiki и открывает PR только с `openwiki/`; несколько уже влитых PR в `docs` могут попасть в одно обновление. Изменение `AGENTS.md` или `CLAUDE.md` генератором считается ошибкой запуска: эти файлы правят как исходник отдельно, затем обновляют wiki. Нет локального таймера, фонового опроса GitHub, запуска модели по `push` или недельного расписания.
5. `scripts/openwiki-check.ts` читает `openwiki/.last-update.json`: требуется `status=complete`, 40-символьный `gitHead`, существующий предок целевого SHA и отсутствие изменения исходных путей между ними. Из сравнения исключается только `openwiki/**`; `AGENTS.md`, `CLAUDE.md`, `site/`, `docs/`, схемы, скрипты и workflow остаются источниками. Проверка принимает явный целевой SHA, поэтому после merge PR wiki её checkpoint может быть старше HEAD на wiki-коммит и всё же считаться свежим. `updatedAt` выводится для наблюдения, но время само по себе не доказывает свежесть. Проверка сообщает исходный SHA, целевой SHA и список изменившихся путей.
6. GitHub Actions без модели проверяет свежесть **только в PR, который меняет wiki**, относительно base SHA на момент проверки. После обычного PR в `docs` wiki может оставаться устаревшей сколько решит владелец; красная проверка на `main` не создаётся. Агент при использовании wiki локально сравнивает её checkpoint с актуальным SHA и при расхождении использует wiki только для поиска, подтверждая факты по каноническим документам. Если явная команда обновления завершается ошибкой, она выводит причину и не открывает PR; последняя успешная wiki остаётся доступной. В PR запрещены секреты и неожиданные пути. Непосредственно перед слиянием PR checkpoint повторно сравнивается с текущим `docs/main`: если base изменился, нужна новая генерация, даже если прежняя проверка PR была зелёной.

## Проверка качества и приёмка

- Сначала в изолированном worktree на актуальном `docs/main` проверить `code` режим: русские страницы, охват тем из пилота, проверяемые Claims и ссылки на существующие исходные файлы. Сравнить ответы D01, C09, C12 минимум в трёх независимых прогонах; затем 12 вопросов из `context-benchmark/cases.json` с чтением wiki и сверкой исходников. Порог: не ниже 33/37 обязательных пунктов, 24/24 проверяемых доказательств и ноль критических ошибок; при провале исправить цель генерации/контент источника и повторить проверку перед публикацией.
- На отдельной копии изменить один исходный документ, запустить `--update`, проверить нужную страницу/Claim и новый `gitHead`; удаление или изменение прежнего утверждения не должно оставлять его как текущий факт. Второй запуск без изменений должен обходиться без генерации страниц.
- Проверки свежести покрывают корректный checkpoint, старую wiki после изменения источника, wiki-only merge, неполный запуск, несуществующий SHA и новый `docs/main` во время открытого wiki PR. CI проверяет только wiki PR; локальный `bun run typecheck && bun run test && bun run build` проходит.
- Из каждого репозитория агент находит одну и ту же wiki, отличает её от источника, сверяет актуальность и может найти исходный документ. Человек открывает `quickstart` из страницы контекста на сайте.

## Принятые здесь проектные решения

Формат публикации через GitHub Markdown и вариант `code` выбраны для хранения wiki рядом с каноническим `docs` и возможности проверить Claims/коммит. Владелец выбрал ручной момент обновления: по его команде локальный Codex с подпиской создаёт PR. CI проверяет свежесть этого PR и не предлагает расписание обновлений.
