# Серверный bootstrap пользователя в BFF — дизайн

Дата: 16.10.2026. Статус: спека утверждена пользователем; реализация документации — по
[плану](../plans/2026-10-16-bff-server-bootstrap.md).

## 1. Цель и границы

В проект BFF модуля №2 добавляется серверная подготовка начальных данных. При открытии приложения
BFF получает текущего пользователя из Go API, вставляет его в собранный `index.html` и возвращает
страницу. Клиент начинает работу с готовым пользователем, без стартового запроса `users.me`.
Для гостя в HTML находится `user: null`. Это работает при перезагрузке, открытии прямой ссылки на
экран и переходе с внешнего сайта, включая GitHub и Telegram в обычном браузере с сохранённой сессией.
Встроенный браузер другого приложения со своим хранилищем cookie может оставаться гостем.

Пользователь — ментор. Результат этой работы — согласованный проект для документации трека;
по нему студенты реализуют BFF, клиент и инфраструктуру. Продуктовый код этим изменением не пишется.

В bootstrap входит только пользователь. Список блокнотов, ячейки, состояние рантайма и остальные
данные клиент получает через tRPC. Интерфейс строится в браузере собственным React команды;
сервер подготавливает HTML-шаблон и данные, без рендера дерева React.

## 3. Решения и замена прежних решений

| Решение | Обоснование | Что заменяется |
| --- | --- | --- |
| В HTML только `{ user }` | Убрать отдельный сетевой этап определения пользователя при старте | Старт приложения через `users.me` |
| HTML-шаблон включён в образ BFF; ассеты — в S3/CDN | Код BFF, HTML и клиентские ссылки принадлежат одному выпуску | HTML из изменяемого корневого `index.html` S3, отдельный promote клиента |
| Bun workspaces + Turborepo, Vite для клиента, Bun build для BFF | Менеджер пакетов, граф задач и сборщики выполняют разные задачи | Подмены Vite на Turborepo не происходит |
| `SameSite=Lax` у cookie сессии | Пользователь должен определяться уже при первом HTML-запросе с внешнего сайта | `Strict`, выбранный для SPA с неперсональным HTML |
| Bun HTMLRewriter и serialize-javascript в JSON-режиме | Преобразовать собранный HTML и безопасно передать обычный JSON | Шаблонизатор EJS/Nunjucks, ручная HTML-склейка, исполняемое присваивание в `window` |
| Нет достоверного ответа Go — HTML 503 с сохранением сессии | Сбой сервиса не должен выглядеть как выход пользователя | Подмена ошибки ответом `user: null` |

## 4. Контракт bootstrap

В исходном `apps/client/index.html` есть ровно один элемент:

```html
<script id="bootstrap" type="application/json"></script>
```

Vite сохраняет этот элемент в клиентской сборке. BFF заполняет его на каждый HTML-запрос.
Форма данных — `BootstrapData` с единственным полем `user`: DTO текущего пользователя или `null`.
Тип пользователя совпадает с результатом процедуры `users.me`; отдельная ручная копия модели
пользователя не создаётся. Тип `BootstrapData` экспортируется из пакета BFF для `import type`
на клиенте, как `AppRouter`. Серверный код, сериализатор и Orval-клиент Go в клиентский бандл не входят.

В JSON нет access/refresh-токенов, сроков токенов, зашифрованной сессии, ключей или служебных ответов Go.
Используется только DTO пользователя, который и так получает браузер через `users.me`.

Перед первым рендером клиент находит элемент `bootstrap`, читает `textContent`, вызывает
`JSON.parse()` и инициализирует стор сессии. `user: null` означает гостя. Наличие пользователя означает
вошедшую сессию для начального интерфейса; каждый последующий запрос к API авторизуется на сервере.
Дублирующего стартового `users.me` нет. Процедура остаётся для явного обновления пользователя.
Вход, регистрация и выход продолжают обновлять клиентский стор своими ответами.

Отсутствующий, повторный или невалидный JSON-блок — ошибка выпуска или запуска, а не признак гостя.
Клиент показывает ошибку запуска без автоматического запроса `users.me`, маскирующего дефект.

## 5. Путь HTML-запроса и общая сессия

Поток: браузер → Caddy → BFF → общий слой сессии → Go `GET /users/me` → вставка JSON → браузер.
Запрос в Go использует тот же Orval-клиент, Bearer и, для двух VPS, `X-BFF-Key`, что и процедуры tRPC.

1. BFF читает и расшифровывает cookie сессии. Cookie нет — пользователь `null`, Go не вызывается.
   Cookie повреждена или refresh уже истёк — гостевой HTML и удаление недействительной cookie.
2. При сессии BFF использует общую с tRPC обработку access: refresh перед истечением, один повтор
   запроса после `401`, объединение одновременных refresh и кеш результата на 10 секунд.
3. Из успешного ответа Go берётся DTO пользователя. Отклонённый refresh или повторный `401`
   подтверждают недействительность сессии: cookie стирается, HTML содержит `user: null`.
4. Новая или удаляемая cookie записывается в заголовки того же HTML-ответа до отправки тела.
5. BFF сериализует `{ user }`, заполняет шаблон и возвращает `text/html; charset=UTF-8`.

HTML-хендлер не вызывает собственный HTTP endpoint tRPC и не подделывает `X-CSRF`.
Общий слой сессии и клиента Go выделяется из транспорта: tRPC использует его после своих проверок
в `createContext`, HTML-хендлер — после определения типа запроса. Логика refresh не копируется.
Это уточняет прежнее решение «CSRF и сессия только в createContext»: CSRF API остаётся там,
а чтение и обновление сессии доступны обоим транспортам.

При ошибке сети, таймауте, `5xx`, `403 s2s_forbidden` или другом неожиданном ответе Go BFF возвращает
HTML-страницу временной недоступности с HTTP `503`. Приложение на ней не запускается, подробности
ошибки клиенту не показываются. Cookie не удаляется. Если refresh уже успешно завершился, новые
токены сохраняются в новой cookie даже на этом ответе: оставлять отозванный старый refresh нельзя.
Сбой не превращается в `user: null`. Таблица ошибок RPC сохраняется: такие ошибки tRPC по-прежнему
передаёт как `BAD_GATEWAY`, а не как HTML 503.

Запросы Go ограничиваются конечным таймаутом общего сетевого клиента; bootstrap не добавляет свою
отдельную политику повторов. Одновременные HTML- и RPC-запросы участвуют в одном механизме refresh.

## 6. Преобразование HTML и безопасность

При старте BFF читает неперсональный шаблон из образа в память и проверяет наличие ровно одного
`script#bootstrap` с `type="application/json"`. Неправильный шаблон или ошибка чтения — отказ старта,
а не раздача HTML без bootstrap. Шаблон после этого не меняется.

Для каждого запроса создаётся свой HTMLRewriter с данными только этого запроса:

- объект `{ user }` сериализуется через `serialize(value, { isJSON: true })`;
- значение `unsafe: true` не используется;
- сериализованный JSON вставляется в script через `setInnerContent` с `html: true`: безопасное
  экранирование для script уже выполнено сериализатором; повторное HTML-экранирование исказит JSON;
- клиент разбирает JSON, не выполняя код из содержимого script.

`type="application/json"` отделяет данные от исполняемого JavaScript, но сам по себе не защищает
от закрывающего `</script>` внутри строки. Поэтому экранирование сериализатором обязательно.
Проверяется восстановление исходных строк после `JSON.parse()`, включая `<`, `>`, `&`, кавычки,
переводы строк и попытку закрыть script.

Все HTML-ответы bootstrap, включая гостевые, и ответы 503 получают `Cache-Control: private, no-store`.
Они не кешируются CDN, Caddy, браузером или BFF как общий готовый HTML. Между запросами разделяется
только исходный неперсональный шаблон. У персонального ответа нет общего ETag или возврата `304`.
Заголовки длины и кодирования берутся от итогового ответа, а не от исходного файла.
Cookie, токены и JSON пользователя не пишутся в логи.

Cookie сессии сохраняет имя `__Host-Http-session`, `HttpOnly`, `Secure`, `Path=/`, отсутствие `Domain`,
AES-256-GCM и срок по refresh; меняется только `SameSite`: `Strict` → `Lax`.
Это осознанное отступление от рекомендации Strict в цитируемом RFC ради bootstrap на внешней навигации.
Внешний GET страницы допускается без `X-CSRF` и с `Sec-Fetch-Site: cross-site`.
Проверки `/api/trpc` сохраняются: `X-CSRF: 1` на каждом вызове, для POST — точный `Origin` и
`Sec-Fetch-Site: same-origin`, если заголовок есть; разрешающего CORS нет.
GET HTML не выполняет изменения предметных данных и logout.

## 7. Маршрутизация и локальная разработка

| Запрос | Обработка |
| --- | --- |
| `/api/trpc` и `/api/trpc/*` | Официальный fetch-адаптер tRPC; ошибки остаются в формате tRPC |
| `/api/v1` и остальные внешние `/api/*` | Недоступны как Go API; не попадают в HTML fallback |
| `/health` | Внутренний liveness BFF, `200 ok`, Go не вызывается; Caddy наружу не публикует |
| Существующие публичные файлы клиента | Раздаются отдельным маршрутом, без bootstrap и запроса пользователя |
| GET клиентского HTML, включая прямую ссылку на экран | HTML-хендлер BFF с bootstrap |
| HEAD клиентского HTML | Статус и заголовки соответствующего GET, без тела |
| Остальные методы и запросы не к HTML/публичным файлам/API | Ошибка маршрутизации, а не персональная SPA-страница |

Маршруты API, служебные и публичные файлы обрабатываются раньше SPA fallback. Он применяется к
GET/HEAD с `Accept: text/html`, поддерживает клиентскую маршрутизацию и не поглощает API-ошибки.
Публичные файлы, которым нужен основной origin, например favicon, robots или manifest, обслуживаются
по явному списку файлов клиентской сборки; произвольный доступ к файловой системе образа закрыт.
Если PWA сохраняет навигационные ответы, персональный HTML исключается из её кеша.

Caddy принимает HTTPS и передаёт HTML и tRPC в BFF. Маршрут, читающий корневой `index.html` из S3,
заменяется этим потоком. JS/CSS и остальные ассеты с адресами CDN продолжают идти напрямую в CDN.

В разработке браузер открывает приложение через BFF, чтобы пройти тот же bootstrap и использовать
same-origin tRPC. Шаблон HTML берётся у Vite dev server, проходит его dev-преобразования, затем общий
bootstrap-преобразователь. Vite сохраняет HMR. Для cookie с префиксом `__Host-Http-` обеспечивается
локальный HTTPS; защитные атрибуты cookie не ослабляются ради dev. Порты и сертификаты относятся
к окружению приложения, а не к новому публичному API.

## 8. Сборка, выпуск и откат

Сохраняются три workspace: `apps/client`, `apps/bff`, `packages/schemas`.

- Bun workspaces управляет зависимостями и линками пакетов.
- Turborepo запускает сборку, тесты и проверку типов с учётом графа и кеша.
- Vite собирает клиент и `index.html`; base ассетов содержит неизменяемый адрес CDN выпуска.
- `bun build --target bun` собирает BFF; serialize-javascript входит в серверный бандл.

Упаковка образа — отдельный шаг после обеих сборок. Она не входит в `build` пакета BFF:
клиент уже зависит от типов BFF, поэтому обратная зависимость `bff#build` от `client#build` создаст цикл.
Граф сборки по-прежнему начинается с зависимостей workspace; упаковка потребляет готовые результаты.
SHA выпуска и адрес ассетов входят в ключ кеша соответствующей сборки клиента.

Контекст Docker меняется с `apps/bff` на корень монорепы. В образ попадают серверный бандл,
клиентский `index.html` и необходимые файлы для основного origin из явного публичного списка.
JS/CSS для CDN хранить в образе не требуется. Точная версия Bun Alpine, запуск от пользователя
`bun` и `/health` сохраняются. Путь шаблона фиксирован внутри образа, не выбирается из URL запроса.

Порядок выпуска из одного коммита:

1. Собрать и проверить клиент и BFF.
2. Загрузить клиентские ассеты в неизменяемый `releases/<sha>/` S3/CDN.
3. Собрать и опубликовать образ BFF по тому же SHA с HTML, ссылающимся на эти ассеты.
4. После успешной загрузки ассетов выкатить образ. Ошибка загрузки запрещает выкладку этого образа.
5. Проверить внутренний `/health`, внешний гостевой HTML с bootstrap и доступность ассета своего SHA.

Браузер получает HTML из работающего образа. Чтения S3, CDN или `current.json` для выбора HTML
во время запроса нет. Отдельное копирование клиентского HTML в корень S3 и promote клиента больше
не управляют этим приложением. Это меняет запланированный CI/CD, а не просто добавляет HTTP-хендлер.

Откат возвращает предыдущий образ BFF вместе с его HTML и сохраняет работоспособность ссылок на его
ассеты. Retention оставляет последние пять клиентских выпусков и дополнительно сохраняет ассеты
текущего и предыдущего образов независимо от их возраста. Нельзя удалять их только потому,
что изменился старый S3-указатель. Миграции Go оцениваются отдельно; откат образа BFF не откатывает БД.

Первый переезд остаётся одним переключением Go/BFF/Caddy с принятым коротким окном недоступности;
ассеты нового клиента загружены заранее. Отдельного шага promote клиента после playbook больше нет.
Три прежние cookie стираются на входе, регистрации и выходе, как в действующем проекте BFF;
старые сессии автоматически в новую cookie не переносятся.

кеширование, разработку, выпуск и проверяемые сценарии. Текущие страницы синхронизируются:

- `bff.md`: добавить bootstrap и новый тип, изменить старт клиента, таблицу cookie,
  маршрутизацию HTML, общий выпуск и раздел «Переключение».
- `bff/contract.md`: добавить контракт `BootstrapData`, type-only импорт, связь с `users.me`;
  подчеркнуть, что bootstrap — HTML-ответ, а не новая процедура tRPC.
- `bff/auth.md`: описать общий слой сессии, Lax и HTML-ответы с обновлённой cookie;
  обновить сценарии внешнего перехода и первого входа; RPC-формат ошибок сохранить.
- `bff/service.md`: добавить HTML-маршрут, чтение и проверку шаблона при старте, ошибки 503,
  упаковку после сборок, контекст Docker из корня и маршрутизацию Caddy.
- Схемы `diagrams/modules/2/bff-contract.json` и `frontend-monorepo.json`: отразить HTML bootstrap,
  импорт типа и связь результатов клиентской сборки с BFF. Описание схем в README сверить с итогом.
- Тесты `scripts/bff-pages.test.ts`, `modules-data.test.ts` и относящиеся к изменённым схемам:
  синхронизировать состав подстраниц, решения, ссылки, заголовки и связи.

Корневые схемы, описание нынешнего CSRF и `frozen-k3s` не меняются: они описывают прод или историю.
Новые GitHub issues, назначения, push, PR и выкладка этим согласованием не поручаются.

## 10. Приёмка и проверка

Будущая реализация приложения проверяется по поведению:

1. Гость получает HTTP 200, валидный `{ user: null }`; Go для определения пользователя не вызывается.
2. Вошедший пользователь получает свой DTO в первом HTML; стартового `users.me` в браузере нет.
3. Перезагрузка и прямая ссылка на экран сохраняют bootstrap; переход с GitHub в том же браузере
   передаёт Lax-cookie и возвращает пользователя в первом HTML.
4. Access перед истечением и `401` от Go обрабатываются общей политикой refresh; новые cookie
   выставляются до тела HTML. Одновременный HTML/RPC не создаёт отдельную гонку refresh.
5. Повреждённая cookie, истёкший или отклонённый refresh дают гостя и удаление недействительной cookie.
6. Сеть, таймаут, `5xx` и S2S-ошибка дают HTML 503, а не гостя; сессия сохраняется. Отдельный сценарий:
   refresh успешен, последующий `users/me` упал — новая cookie всё равно приходит с 503.
7. Строка пользователя с `</script>` не создаёт новый HTML-элемент и после `JSON.parse()` восстанавливается
   без искажения. Клиентский бандл не содержит сериализатор и серверные зависимости.
8. Два параллельных HTML-запроса разных пользователей возвращают каждому только его данные.
   Ответы не кешируются как общий HTML, в том числе PWA при появлении offline-режима.
9. Нет/два bootstrap-элемента в собранном шаблоне — отказ старта BFF. Повреждённый bootstrap на клиенте
   показывает ошибку запуска, не выдаёт пользователя за гостя.
10. API, служебные пути и публичные файлы не попадают в bootstrap; tRPC сохраняет свои CSRF и конверты.
11. Работают Bun workspaces, Turborepo и Vite; упаковка не создаёт цикл build-зависимостей.
12. Ассеты публикуются до выкладки; HTML и бандл BFF из одного коммита. Откат образа возвращает
    HTML предыдущего выпуска, ассеты которого сохранились.

В задаче на документацию выполняются `bun run modules:check`, `bun run typecheck`, `bun run test`,
`bun run build`, а для изменённых схем — validate → check → render → осмотр PNG.
На собранном сайте проверяются новая подстраница, её пункт меню, ссылки и схемы.
Проверки приложения из списка выше остаются критериями для студенческой реализации, а не
объявляются пройденными по факту изменения Markdown.

## 11. Не входит

- Продуктовая реализация BFF, фронта, Go, CI/CD или Ansible в этой задаче docs.
- Данные экранов в bootstrap, SSR компонентов React, SEO-рендер, канарейка и feature flags.
- Новое серверное хранилище сессий, несколько экземпляров BFF или переработка Redis-трека.
- Выбор SSE/WebSocket для исполнения файлов: это отдельная несогласованность прежних документов,
  данный bootstrap её не решает.
- Публикация сайта, изменение задач команды или мердж без отдельного поручения пользователя.
