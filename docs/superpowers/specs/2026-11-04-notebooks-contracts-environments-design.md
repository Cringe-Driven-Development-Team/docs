# Контракты блокнотов и подтрек окружений

Статус: согласован пользователем 04.11.2026.

## Задача и выбранный подход

Студентам нужен один вход в план блокнотов и справочник по двум границам API: браузер → BFF и BFF → Go. Сейчас страница «Сохранение и исполнение» описывает сценарии и диаграммы, но не даёт таблиц входов/результатов. Отдельный трек «Автоподнятие VPS под каждый новый блокнот» сохраняет ранние архитектурные варианты и выглядит самостоятельным направлением.

Пользователь выбрал две отдельные таблицы с JSON-примерами по образцу «Операции API» в 2FA и включение окружений в общий трек блокнотов. Размер работы: изменение нескольких связанных страниц и данных навигации, без изменения приложения или API. Этот документ фиксирует дизайн; реализация начинается после его согласования и плана.

Рассмотренные подходы:

1. **Две таблицы контрактов на существующей странице — выбран.** Явно разделяют tRPC и HTTP, позволяют показать внутренние чтения агрегаторов и примеры. Цена: потребуется сопоставлять строки двух таблиц; связи и ссылки указываются явно.
2. Одна сквозная таблица tRPC → HTTP → результат. Компактна для прокси, но агрегация `notebooks.get` и `runtime.updates` с несколькими чтениями и JSON делает строки чрезмерно широкими.
3. Отдельный справочник на новой странице. Уменьшает размер текущей страницы, но разносит контракты и уже согласованные сценарии. Для этого изменения не выбран.

Окружения становятся подтреком с сохранением файла `notebook-vps.md`, исполнителей и привязок. Полное поглощение страницы общим треком скрывало бы отдельную работу бэка/devops; оставить её самостоятельной противоречило бы единой точке входа.

### Открытие и общий результат

Исправить безусловную фразу «Браузер вызывает notebooks.get». Два пути:

1. Прямой GET страницы: HTML-обработчик вызывает общий загрузчик BFF, сериализует данные в существующий server bootstrap; клиент использует preloaded без начального tRPC-запроса.
2. SPA-переход без подходящего bootstrap: `notebooks.get` вызывает тот же загрузчик и возвращает ту же форму данных. HTML-обработчик не делает HTTP-запрос к собственному tRPC.

#37 обеспечивает metadata + content в обоих путях; #51 добавляет active session и очередь. Сохранить конверт bootstrap с пользовательскими данными; не задавать новую несовместимую форму HTML сверх согласованного общего результата. Показать один пример итогового результата загрузчика `{notebook, active_session, runtime_queue}` и объяснить его использование в bootstrap, не выдумывая нового публичного endpoint.

Метаданные/content/active читаются параллельно; hash и cells только из одного content. Это не общая транзакция всех чтений. Очередь читается после active только для сессии текущего блокнота; другая сессия остаётся в active_session, runtime_queue тогда null. Для своей сессии пустая очередь — объект с items:[], отсутствие сессии — null. Ошибки не превращаются в успешные пустые данные. Открытие не читает весь журнал, не делает запрос на каждую ячейку и не запускает/продлевает runtime.

### Таблица «Фронт → BFF»

Четыре столбца: **tRPC-операция и вид (query/mutation)**; **когда вызывается / роль BFF**; **входные данные**; **результат**. В строках — короткие JSON-примеры входов и ответов; общие требования авторизации вынести перед таблицей, а не повторять столбцом во всех строках.

Одиннадцать строк: `notebooks.get`; `cells.create`, `cells.update`, `cells.move`, `cells.delete`; `runtime.start`, `runtime.execute`, `runtime.executeAll`, `runtime.stop`, `runtime.activity`, `runtime.updates`.

- Поля и названия из актуальных #37/#51, без нового API. Ссылки на соответствующие HTTP-операции второй таблицы; для агрегаторов перечислить внутренние чтения и порядок зависимых вызовов.
- CRUD: notebookId/hash/cellId, kind/source/index по операции; ответы `{hash,cell}` или `{hash}`. Передача hash в HTTP If-Match относится к BFF, браузер не формирует Go-заголовки.
- Execute: execution_id/cell_id/source_hash, без source. Batch: один request_id и фиксированный упорядоченный список code-ячеек, один HTTP batch. Принятая команда не означает законченный результат; полный execution_ids сохраняется для отслеживания.
- updates: вход sessionId/after/executionIds и ответ session/runtime_queue/events/next_cursor/has_more/executions по #51. Показать один небольшой согласованный пример, не полный журнал. Зафиксировать курсор Go, одну страницу событий за вызов и объединение/дедупликацию ID для чтения конкретных исполнений; предел executionIds 100, последовательное дочитывание страниц/порций. Это агрегатор, не обещание транзакционно атомарного снимка.
- activity отправляется после реального изменения source не чаще раза в 30 секунд; polling — не activity. runtime.updates используется для дальнейшего наблюдения независимо от способа первоначальной загрузки.

Таблица описывает полезную нагрузку процедур, а не транспортный JSON-конверт tRPC. Не представлять HTTP-коды Go как коды успешного ответа tRPC.

### Ошибки и статус контракта

Компактная отдельная таблица: **операция/условие**, **ошибка Go**, **что сохраняет/возвращает BFF**, **реакция UI**. Включить подтверждённые в источниках группы: авторизация/владение, валидация, notebook_conflict, active_session_exists с публичными данными сессии, несовпадение source, переполнение очереди, недоступность runtime и сбой внутреннего чтения агрегатора.

Не придумывать новые error envelopes и соответствия tRPC-кодов. Использовать общий GoError/unwrap и существующий контракт BFF; ограничения текущей реализации и целевые требования #51 различать. При отсутствии точного соответствия в источниках явно назвать непроверенную часть, а не дополнять контракт предположением. Ошибки HTTP/bootstrap обрабатываются существующим путём страницы; JSON tRPC-ошибки не вкладываются вместо данных bootstrap.

Оговорка про hash остаётся видимой до таблиц и в прежнем `#статус-хэша`: UI разрабатывается по целевой семантике #37/#51, текущий Apidog/backend#13 пока описывают влияние outputs. Таблицы не исправляют контракт сами и не обещают готовность реализации. Не вводить поддержку двух семантик/старых endpoint как обход.

Проверить светлую/тёмную темы, обычную и расширенную ширину чтения. Существующие диаграммы остаются интерактивными и привязанными к пояснениям.

1. На общем треке и в меню/графе есть подтрек «Окружения исполнения», редактор остаётся рядом. Старый URL notebook-vps открывается напрямую и из старых ссылок, исполнители/привязки сохранены. Документ contract остаётся документом, а не третьим треком.
2. Нигде в обновлённой текущей модели не обещается VPS при создании блокнота, отдельный оператор-микросервис или новая views.notebook. Исторические исследования явно отделены, незавершённые работы не объявлены завершёнными.
3. Две основные таблицы содержат 11 tRPC и 16 HTTP-операций, входы/результаты и примеры; связь агрегаторов с внутренними чтениями понятна. Ошибки и оговорка по hash видны. bootstrap описан до первого возможного запроса браузера.
4. Все JSON-примеры парсятся; полные примеры соответствуют актуальным схемам, сокращённые подписаны, показанные поля/значения не противоречат схеме. Два слоя не расходятся по ID, hash/source_hash, null/пустой очереди и required-полям. Конкретные значения не содержат реальные секреты/адреса.
5. Сохраняются прежние якоря, две Mermaid-последовательности и обзор компонентов. Новые ссылки ведут на существующие цели в корне сайта и превью ветки.
6. Проверки по изменению: modules:check, typecheck, test, Docker build/site:check; штатный браузерный harness для hierarchy/scroll и визуальная проверка таблиц при 1440/360 px, в обеих темах, с клавиатурой. Проверить отсутствие регрессии таблицы 2FA; новые парсеры Markdown/JSON Schema и тестовые фреймворки не создавать.
7. После реализации и ревью — PR в main с превью, проверка CI и фактической публикации Pages. Слияние не входит без отдельного поручения.
