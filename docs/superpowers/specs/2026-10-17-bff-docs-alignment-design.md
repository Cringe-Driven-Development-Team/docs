# BFF: документация MVP и собственный tRPC в модуле №3

Дата: 17.10.2026. Статус: принято пользователем 17.10.2026 переходом к writing-plans и SDD; выполнение — по [плану](../plans/2026-10-17-bff-docs-alignment.md).

## 1. Цель и согласованное понимание

Согласовать страницы, треки и схемы документации с решениями, принятыми при обсуждении BFF
и уточнении задач frontend#2, #4, #5, #44, #45 и #46. Студент должен видеть одинаковые
требования на сайте и в своей задаче, понимать добавление процедуры и ограничения MVP.

Пользователь подтвердил:

- Модуль №2 использует официальные `@trpc/server`, `@trpc/client` и `zod`.
- В модуле №3 пишутся **собственные клиент и сервер tRPC**, а не только клиент; свой Zod
  и свой React Hook Form уже относятся к этому модулю.
- Новые автотесты приложения в MVP не требуются: показанные примеры тестов клиента надо убрать.
- MVP выпускается с коротким окном недоступности; канарейка — отдельный следующий этап.
- Нужно объяснить контракт tRPC, SameSite, mTLS; исправить обрезку подписи и тяжёлое форматирование.

Это работа в репозитории `docs`. Она описывает будущую реализацию BFF и не объявляет её
работающим продом. Продуктовый код, создание задач, изменение GitHub-назначений и полей доски не входят в реализацию.

## 3. Выбранный подход и границы

Один согласованный пакет правок сайта: обновить описание MVP, существующий подтрек клиента,
создать трек своего tRPC в модуле №3 и исправить связанные схемы/проверки.

Точечное удаление подписи `trpc-client` оставило бы противоречия на страницах и в графе модулей.
Полное проектирование новой RPC-библиотеки или канарейки сейчас расширило бы задачу за пределы
запроса. Здесь задаются цель и границы будущего трека; подробный API собственной библиотеки
проектируется перед её реализацией.

| Решение | Было | Должно стать |
| --- | --- | --- |
| tRPC в модуле №2 | свой клиент, официальный сервер | официальный клиент и сервер 11.x совместимых версий |
| Свой tRPC | свой клиент в модуле №2 | отдельный трек модуля №3: клиент и сервер |
| Тесты MVP | примеры/требования разработки тестов своего клиента | ручная приёмка; существующие проверки репозитория сохраняются |
| Контракт | механизм типов объяснён кратко | явный флоу добавления процедуры, без отдельной генерации клиента |
| SameSite и S2S | краткие формулировки и длинный абзац | примеры поведения и короткие смысловые пункты |
| Выпуск | принято короткое окно недоступности | то же MVP-решение плюс отдельное объяснение будущей канарейки |

## 4. Модуль №2: официальный tRPC и контракт

### 4.1. Клиент

В `bff.md`, `bff/contract.md` и `trpc-client.md`:

- Указать официальные `@trpc/client` и `@trpc/server` в модуле №2, официальный Zod на BFF.
- Пример создаёт клиент через `createTRPCClient<AppRouter>` и `httpBatchLink`, endpoint
  `/api/trpc` на том же origin; общий транспорт добавляет `X-CSRF: 1` и
  `credentials: 'same-origin'`. Батчинг и ограничение `maxURLLength: 2000` задаются link,
  а не собственной реализацией протокола.
- Ошибки — `TRPCClientError`, `data.code`, `data.appCode`, `data.zodError`; убрать
  требование собственного `TrpcError`. Серверные правила `errorFormatter` сохраняются.
- `AppRouter`, `BootstrapData`, вывод типов входов/ответов импортируются как типы;
  серверный runtime-код не попадает в клиентский бандл.
- Не утверждать, что сторонних runtime-библиотек на клиенте нет. Собственные React/Zustand
  команды продолжают использоваться; разрешение официального tRPC не меняет остальные библиотеки.
- Текущая ручная проверка форм в модуле №2 сохраняется. Общие схемы в браузере и собственная
  реализация Zod относятся к модулю №3; новый Zod на клиенте ради чтения bootstrap не добавляется.

Из раздела «Клиент» удалить два блока тестов с подставным `fetch` и требование их разработки
в MVP. Вместо них дать короткую ручную приёмку: успешные query/mutation, ошибка полей,
`UNAUTHORIZED`, отсутствие клиентского refresh. Не удалять тесты самого репозитория `docs`.

### 4.2. Как добавить процедуру

Добавить в `contract.md` раздел «Как добавить процедуру» после «Роутер»:

1. Согласовать имя, query/mutation, вход, результат, ошибки и необходимость авторизации.
2. Если не хватает операции Go — сначала изменить его контракт Apidog и реализацию; выполнить
   `bun run sync`. Если достаточно уже существующих операций Go, новый OpenAPI не нужен.
3. Добавить процедуру в роутер tRPC. Для passthrough использовать подходящие схемы Orval;
   собственный вход агрегированной процедуры описывать в BFF на Zod. Hono подключает общий
   адаптер, отдельную Hono-ручку на каждую процедуру не создают.
4. В обработчике вызвать общий клиент Go, при необходимости собрать несколько ответов.
   Предметная логика остаётся в Go; BFF подготавливает данные для интерфейса.
5. Экспортировать `AppRouter`; TypeScript выводит методы и типы официального клиента.
   Кодогенерации клиента BFF → браузер нет.
6. Использовать `api.<процедура>.query(...)` / `.mutate(...)` на фронте и выполнить ручную
   проверку вместе с `typecheck`.

Показать короткий согласованный пример существующей процедуры, её вызова и типов. Пример
агрегации `views.notebook` оставить явно будущим, привязанным к появлению Go API рантаймов.
Сначала согласовать контракт — процесс работы; источник типов в выбранной архитектуре —
роутер tRPC. Не называть автоматически выведенный роутер независимой OpenAPI-спецификацией.
Обязательную runtime-валидацию всех ответов и второй набор DTO эта правка не вводит.

### 4.3. Задачи и опубликованные адреса

Сохранить существующий адрес `/modules/2/tracks/trpc-client`, id `trpc-client`, `part_of: bff`
и владельца `iRedTea`. Переименовать title в описание подключения официального клиента,

## 5. Модуль №3: собственные клиент и сервер

Создать `site/modules/3/tracks/trpc.md`, title «Свой tRPC: клиент и сервер», label «tRPC»,
`area: front`, `do: { iRedTea: front }`, `mentors: [YarikMix]`. Владелец сохраняет направление
прежнего своего tRPC-клиента; это видимая часть данного дизайна, а не новое назначение issue.
Самостоятельный трек: `part_of` на BFF другого модуля не ставится.

На странице три смысловые части:

- **Клиент:** типизированные вызовы процедур, HTTP query/mutation, батчинг, заголовки и разбор ошибок.
- **Сервер:** роутер и процедуры, контекст/middleware авторизации, разбор входа, типы входов/ответов,
  ошибки и HTTP-адаптер для Hono/Bun. Это реализация серверной части tRPC, а не только клиента Go.
- **Интеграция:** заменить официальные библиотеки в приложении собственными реализациями,
  сохранив используемые процедуры, bootstrap, CSRF, сессии и пользовательское поведение.

Граница — необходимое приложению подмножество tRPC, а не полный клон всех возможностей библиотеки.
Совместимость контракта означает сохранение используемого HTTP RPC и типизированного API;
точное публичное API и размещение пакетов собственной реализации требуют её отдельного дизайна.
Ссылки на `frontend-packages` объясняют размещение собственных командных библиотек без выдачи
выдуманных имён/версий будущих пакетов за существующие.

Связать трек с Zod через `related` того же модуля. В `zod.md` уточнить последовательность:
собственный Zod поддерживает Standard Schema/типизацию и подключается к BFF; при внедрении своего
tRPC сервер должен сохранить этот интерфейс. Не обещать, что в конце модуля №3 сервер всё ещё
официальный. Меню/граф получают третий трек из данных; ручной sidebar не нужен.
Issue #46 остаётся во втором модуле и не переносится в новый трек. Новые issue не создаются.

## 6. Понятная безопасность

### 6.1. Strict и Lax

В `auth.md` после рекомендации RFC о Strict и в кратком объяснении bootstrap показать:

| Начало обычной GET-навигации | Strict | Lax |
| --- | --- | --- |
| Прямой ввод адреса или закладка | cookie отправляется | cookie отправляется |
| Ссылка с другого сайта, например GitHub | cookie не отправляется в первоначальном запросе | cookie отправляется |

Условия cookie (хост, HTTPS, срок) считаются выполненными; таблица описывает обычный переход,
а не произвольную цепочку редиректов. Браузер учитывает инициатора, хотя конечный URL одинаков.
При Strict cookie не удалена: первоначальный HTML гостевой; следующий same-site запрос может
её получить, если приложение предусмотрело восстановление. У нас выбран Lax, чтобы пользователь
сразу появился в первом HTML без дополнительного стартового `users.me`.

Объяснить цену: внешний top-level GET может прийти с cookie, поэтому он не меняет предметные
данные и не выполняет logout. POST/RPC остаются защищены `X-CSRF`, Origin и Fetch Metadata.
Различие same-site/cross-origin для поддомена и отдельное хранилище встроенного браузера сохраняются.
Не менять политику cookie или три уже опубликованных CSRF-подраздела/схемы.

### 6.2. S2S, mTLS и доступ к VPS2

В «Две VPS» разделить длинный пункт S2S на короткие подпункты: назначение ключа; проверка до
Bearer; 403 `s2s_forbidden`; реакции BFF (RPC 502, HTML 503, без refresh/удаления сессии);
хранение; ротация старого/нового ключа. Смысл всех существующих правил сохраняется.

mTLS раскрыть как TLS с взаимной проверкой сертификатов BFF и Go: шифрует канал и подтверждает
идентичность обеих сторон. Общий `X-BFF-Key` подтверждает знание секрета, но не шифрует HTTP.
Внедрение mTLS требует сертификатов, доверия и ротации и не становится требованием MVP.
Принятый риск HTTP внутри частной сети описать прямо, не представлять её изоляцию как шифрование.

`ProxyJump`, inventory, SSH forwarding и firewall объяснить как части инфраструктурного переноса
Go/Postgres на приватную VPS2. У BFF в Compose/Caddy на текущей VPS и у выноса на VPS2 разные
результаты; не подменять их общей infra#52. Дать ссылку на infra-репозиторий и честно отметить,
что отдельные задачи нужно оформить; номеров ещё не заведённых задач не выдумывать.

## 7. Выпуск MVP и будущая канарейка

Переформатировать «Переключение» в последовательность: ассеты → образ BFF со своим HTML →
согласованное переключение Go/BFF/Caddy playbook → проверки → возможность отката.
Сохраняются отсутствие отдельного promote клиента и очистка старых cookie с их Path.
Первый переезд требует повторного входа; обычный релиз с прежним `SESSION_KEY` сессию не сбрасывает.

В `bff.md`, `service.md`, `bootstrap.md` согласовать:

- MVP: один экземпляр BFF, короткое окно недоступности допустимо; health/readiness после проверки
  конфигурации/шаблона, конечные таймауты и корректное завершение запросов. Не придумывать новый
  публичный readiness endpoint: текущий внутренний `/health` остаётся liveness без вызова Go.
- BFF и HTML одного SHA, неизменяемые CDN-ассеты, упаковка вне `bff#build`, защищённый retention
  текущего/предыдущего выпусков и откат образа сохраняются; #4 автоматизирует этот выпуск.
- Канарейка — отдельное последующее развитие: сначала небольшой стабильный сегмент пользователей,
  затем расширение доли по результатам ошибок/задержек, возврат трафика при ухудшении.
- Предпосылки канарейки: согласованное направление HTML/RPC пользователя; читаемые обеими версиями
  cookie; безопасный refresh между экземплярами; совместимость API с открытыми вкладками;
  безопасные изменения Go/БД и откат. Совместный HTML/BFF не обновляет JavaScript открытой вкладки.
  Текущий in-memory single-flight на 10 секунд не является общей блокировкой между процессами.

Не внедрять Redis, распределённые блокировки, сегментацию трафика, новую платформу деплоя
или правило N/N+1 в MVP. Не объявлять graceful reload Caddy достаточным условием канарейки.

## 8. Схемы и обрезка

- `frontend-monorepo.json`: убрать `trpc-client` из группы командных npm-пакетов. Официальные
  `@trpc/client`, `@trpc/server`, `zod` обозначить отдельным внешним npm-блоком/выноской,
  визуально отделённой от `@cdd-team/react` и `@cdd-team/zustand` из `frontend-packages`.
  Не изображать официальные пакеты как выпускаемые командой.
- Сохранить три workspace, type-only связи, Vite/Bun, общий образ после обеих сборок и CDN по SHA.
  Убрать обязательный шаг `test` из схемы MVP; существующие тестовые задачи могут сохраняться
  в репозитории приложения без требования писать новые тесты в этой работе.
- `bff-contract.json`: проверить подписи клиента и серверного tRPC, уточнить официальный tRPC
  в модуле №2 там, где требуется. Генерация Apidog → Orval → Go-клиент/схемы остаётся прежней.
  Новую генерацию BFF-клиента и вторую OpenAPI-спеку не рисовать.
- Mermaid «Было и стало»: сократить длинную подпись BFF → Go до метода авторизации/`GO_API_URL`,
  полный пример адреса и пояснение вынести в соседний текст. Результат на собранной странице —
  подпись целиком видна, включая нижнюю строку, без обрезки.
- Если обрезка подтверждённо зависит от обёртки Mermaid, допускается минимальная правка
  разметки/стиля этого блока в `custom.css` с проверкой остальных Mermaid. Общую логику
  масштаба/панорамирования Eraser-просмотрщика не менять.

JSON правится по `eraser-diagrams`: validate → check → warm/render → осмотр PNG. Собственные
цвета статусов и лишние схемы не вводятся. Существующие bootstrap/CSRF-схемы и их имена сохраняются.

## 11. Не входит и следующий этап

Нет продуктового кода, GitHub-issue/board изменений, назначений новых issue, выкладки приложения,
правок root/frozen-схем или текущего раздела `/security/csrf/`. Старые спеки/планы не переписываются.
Детальная спецификация своей RPC-библиотеки, реализация канарейки и новые инфраструктурные задачи
оформляются отдельно. Локальный сервер для чтения пользователя не останавливается.

После ревью и принятия этой письменной спеки — `superpowers:writing-plans`; затем выбранное
пользователем исполнение. Написание спеки не означает разрешение начать править сайт.
