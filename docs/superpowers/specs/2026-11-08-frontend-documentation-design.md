# Раздел Frontend для подготовки к РК2

Статус: проект спецификации, ожидает согласования владельца. Дата: 08.11.2026.
Репозиторий реализации: `Cringe-Driven-Development-Team/docs`.

## Зачем

Перед рубежным контролем 9 ноября студенты должны уметь объяснять устройство
собственного фронтенда и находить соответствующий код. В документации уже есть
офлайн-режим, безопасность и архитектура, но нет связного объяснения запуска
клиента, роутинга, сборки, стилей, состояния и обмена данными.

Создаём раздел Frontend: обзор со сквозным сценарием открытия и редактирования
блокнота и 11 тематических страниц. Это постоянная документация с учебными
объяснениями, которую можно использовать и после РК.

## Согласованные решения

- Обзор включает устройство монорепы, карту основных файлов и сквозной сценарий
  открытия и редактирования блокнота.
- Отдельные подразделы: роутинг, сборка и разработка, стили, запуск приложения,
  компоненты и рендеринг, управление состоянием, запросы и ошибки, сессия и
  авторизация, проверка изменений, командные пакеты, BFF.
- BFF переносится внутрь Frontend и расширяется до объяснения серверной части
  фронта. Нынешние результаты проверки сохраняются с датой и границами проверки.
- Страница командных пакетов описывает назначение, исходники, подключение,
  выпуск версий и обновление зависимостей.

## Рассмотренные подходы

1. **Полноценная страница BFF внутри Frontend.** Даёт единую точку входа в серверную
   часть, но требует развести материал с запуском, запросами и сессией. Пользователь
   выбрал этот вариант: он помогает студенту собрать общую картину.
2. **Перенос только существующего отчёта BFF.** Меньше нового текста, а объяснение
   устройства распределено между остальными страницами. Отклонён: отчёт о проверке
   не даёт самостоятельного объяснения BFF.

Общий раздел Frontend с подстраницами выбран в обсуждении. Одна длинная страница
усложнила бы повторное обращение к отдельной теме; независимые пункты верхнего
уровня не дали бы согласованного маршрута изучения.

### Сквозной сценарий

Обзор прослеживает один конкретный путь: вошедший пользователь напрямую открывает
свой блокнот, получает HTML с bootstrap, клиент показывает блокнот, пользователь
меняет содержимое ячейки, изменение проходит по существующему пути сохранения.
Отдельно кратко сопоставляется открытие через SPA-переход.

Последовательность сохранения, имена процедур, место состояния и обработка ошибки
должны быть взяты из актуального кода. Не приписывать проекту автосохранение,
оптимистические обновления или иной механизм без проверки. Если часть сценария
не реализована, прямо обозначить границу и показать существующий участок; исправление
продукта не входит в эту задачу. Запуск Python в сценарий не входит.

Обзор объясняет связи и ведёт к подробностям, а не повторяет полные тексты подразделов.
В тематических страницах используются те же сущности и реальные файлы приложения.

### Глубина объяснений — предложение автора

Страница отвечает: как механизм работает, почему используется, где находится код,
какие последствия он имеет для пользователя. В конце — несколько коротких вопросов
для самопроверки с ответами в основном тексте, без отдельной экзаменационной системы.

Для командных React, router и Zustand объясняются механизмы, необходимые для чтения
приложения: обновление UI, подписки, переходы и проверки маршрутов. Полный построчный
разбор библиотек не входит. Нельзя переносить гарантии официальных React/TanStack/Zustand
на командные реализации без сверки исходников соответствующей версии.

Короткие примеры берутся из проекта. Новые условные фрагменты явно называются примерами.
Схемы применяются там, где проясняют последовательность; выбор точных схем и примеров
остаётся исполнителю. Достаточно существующих средств Markdown/VitePress; новые
виджеты и зависимости не требуются.

## Связи с существующей документацией

- Офлайн-режим остаётся самостоятельным разделом. Общая сборка ссылается на устройство
  SW и PWA; не копирует подробности регистрации, кеширования и публикации PWA.
- Безопасность остаётся самостоятельной. BFF и сессия объясняют необходимую границу
  ответственности и ссылаются на канонические CSRF/XSS/CSP.
- Архитектура сохраняет общепроектный уровень, Frontend объясняет код своего компонента.
- `project-context.md` остаётся владельцем карты репозиториев и пакетов. `packages.md`
  объясняет их использование и выпуск, ссылаясь на эту карту и исходники владельца.
- В обзор продукта, текущее состояние и карту владельцев добавляются только необходимые
  ссылки. Текущее состояние продукта не объявляется заново проверенным.
- Модули сохраняются как история и планы; меняются необходимые ссылки на перенесённый
  BFF, без объявления всего трека выполненным.

## Перенос BFF

Текущий `site/documentation/bff.md` переезжает в
`site/documentation/frontend/bff.md`. Старый пункт верхнего уровня удаляется из меню.
В `PAGE_REDIRECTS` добавляется:

```ts
{ file: "documentation/bff.html", target: "frontend/bff" }
```

Существующие внутренние ссылки переводятся на новый адрес, включая ссылки из
`current-state.md`, архитектуры и трека BFF. Там, где речь об историческом наблюдении,
ссылка ведёт непосредственно в соответствующий раздел новой страницы.

Прежние даты, SHA, таблица наблюдений, ограничения и источники сохраняются в исторической
части. Прежние утверждения о непроверенных сценариях явно относятся к проверке
31.10.2026, а не становятся оценкой реализации на дату новой документации.

До переноса взять фактические ID заголовков из исходной собранной/опубликованной страницы.
Сохранить их на новой странице по одному разу, включая прежний H1, если на него есть
якорь. Проверить переход по старому URL с fragment: одного совпадения ID недостаточно,
переадресация должна донести fragment до новой страницы. Если текущий механизм его
теряет, минимально исправить общий механизм и проверить соответствующим тестом.

## Источники и статус сведений

Описание реализации привязывается к конкретным актуальным SHA frontend и
frontend-packages, полученным при подготовке страниц. Ссылки на код содержат SHA и
строки, проверенные чтением удалённого файла. Версии командных пакетов сопоставляются
с lockfile приложения; новая версия в main владельца сама по себе не доказывает
поведение версии, используемой приложением.

В начале страниц явно указать: это объяснение реализации по коду на выбранном SHA;
продовые проверки приведены отдельно там, где они есть. Не выдавать сквозной учебный
разбор за успешно пройденный сценарий на проде. Новая полная проверка приложения на
проде не является условием подготовки этого раздела; неизвестное остаётся неизвестным.

На скриншоте требований РК прямо назван Babel и отдельно pre/post-обработка CSS.
Страница сборки обязана честно назвать фактический преобразователь клиентского кода,
а страница стилей — фактическую обработку CSS. Наличие Babel в транзитивных
зависимостях Workbox не считать доказательством Babel-транспиляции приложения.
Не объявлять соответствие требованиям преподавателя без основания. Подключение
Babel, замена сборщика или другое изменение продукта не входит в эту задачу.

## Объём изменений и ограничения

Меняются страницы в `site/documentation/frontend/`, прежняя BFF-страница, навигация,
необходимые ссылки и тесты, список переадресаций. Спека и план находятся в docs.

Код приложения, API-контракт и зависимости приложения не изменяются. Генерируемая
OpenWiki не редактируется и не обновляется. Не добавляются legacy-режимы или требования
безостановочного развёртывания. Не создаётся отдельная страница о командных пакетах
вне согласованного Frontend и не дублируются существующие офлайн/безопасность.

Исполнитель выбирает конкретные фрагменты кода, заголовки внутри страниц и небольшие
схемы, сохраняя состав раздела, границы тем и различение кода/планов/наблюдений.

## Приёмка и проверки

1. Обзор и все 11 подразделов доступны из дерева Frontend; соседние разделы сохранены.
2. Обзор связывает открытие и изменение блокнота с реальными точками кода; отмечены
   непроверенные/не реализованные части, если такие обнаружены.
3. Каждая страница объясняет тему через код проекта и содержит проверенные ссылки
   на исходники. Специфика командных библиотек не подменяется поведением оригиналов.
4. У BFF есть объяснение устройства и сохранённое датированное свидетельство;
   старый адрес и старые fragments работают в корне и превью ветки.
5. Проверки страниц охватывают структуру, значимые решения и новые ссылки с якорями
   по правилам docs-site. Обновлены тесты навигации и `PAGE_REDIRECTS`.
6. Перед коммитами реализации проходят `bun run modules:check`, `bun run typecheck`,
   `bun run test`, `bun run build` (при отсутствии Docker — `DIAGRAMS_NATIVE=1`).
7. Собранный сайт проверен через `check-readability.ts`: `hierarchy scroll`,
   при добавлении схем также соответствующие проверки их отображения. Перенос адреса
   проверяется после сборок корня и вложенной `SITE_BASE`. Проверяется реальный HTML.
8. При дальнейшем создании PR указано превью. После согласованного слияния проверяются
   публикация Pages и новые страницы на проде; сама эта спека не разрешает слияние.
