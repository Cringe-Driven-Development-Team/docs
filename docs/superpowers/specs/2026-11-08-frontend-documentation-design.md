## Выбранный подход

Общий Frontend с подстраницами выбран пользователем. Обзор связывает темы одним сценарием.
Для BFF рассмотрены два варианта:

1. **Полноценная страница серверной части фронта с исторической проверкой.** Выбрана
   пользователем: даёт единую точку входа; границы с запуском, запросами и сессией задаются явно.
2. **Перенос только старого отчёта**, объяснения распределяются между соседями.
   Меньше текста, но отчёт не объясняет устройство BFF; вариант отклонён.

## Сквозной сценарий

Вошедший пользователь открывает свой блокнот на устройстве с доступным редактором.
При `(pointer: coarse)` приложение включает просмотр; это ограничение указывается явно.

1. BFF выдаёт HTML с пользователем и notebookPage: метаданные, content с согласованными
   hash/ячейками, сведения активной runtime-сессии и очереди.
2. Клиент проверяет bootstrap, заполняет session/preloaded и запускает роутер/рендер.
   Страница забирает preloaded; при SPA-переходе без него использует notebooks.get.
3. Cell показывает черновик либо подтверждённый source; ввод вызывает editSource.
   Стор уведомляет подписчиков, интерфейс показывает текст и статус сохранения.
4. Через 500 мс без ввода или при явном commit правка попадает в очередь. IME и лимит
   UTF-8 учитываются. Очередь отправляет notebookId/cellId/source/hash в cells.update.
5. BFF валидирует вход, формирует If-Match и вызывает Go.
6. Ответ обновляет confirmed и hash. Черновик снимается только при совпадении с
   отправленным текстом: новый ввод во время запроса сохраняется.
7. Короткое ответвление показывает конфликт или неопределённый результат и сверку.
   Подробные переходы, сохранность черновиков и выбор пользователя — в state/requests.

Редактирование не заменяется примером create/delete. Запуск Python не входит в
сквозной сценарий; уже существующие runtime-данные и стор отмечаются в карте приложения.
Обзор объясняет связи и ведёт к подробностям, не копирует устройство всей очереди.

## Глубина и форма

В начале страницы — краткий ответ и статус сведений, далее механизм, причина решения,
реальные точки кода и несколько вопросов для самопроверки с ответами в тексте.
Внутренности библиотек раскрываются для объяснения используемых механизмов, без
построчного разбора всего пакета. Обязательны шесть небольших Mermaid-схем рядом
с поясняющим текстом: в обзоре — открытие, ввод и подтверждение через client/BFF/Go;
в startup — bootstrap, инициализация и остановка при повреждении; в routing —
прямой URL через BFF и SPA-история с деревом, beforeLoad и Outlet; в rendering —
событие Cell, подписка/selector и render/reconcile/commit; в state — ответ v1 при
новом draft v2 и отдельно восстановление неизвестного исхода/409 с выбором версии.
Схемы сохраняют ограничения соседнего текста и не подменяют подробный протокол.
Используются существующие средства VitePress, без новых виджетов/зависимостей.

Офлайн, безопасность и общая архитектура сохраняют своих владельцев: Frontend даёт
резюме границы и ссылку. Карта репозиториев остаётся в project-context. Модули
сохраняются как планы/история, выполненными только из-за документации не объявляются.

## Перенос BFF

`site/documentation/bff.md` переезжает в `site/documentation/frontend/bff.md`.
В PAGE_REDIRECTS добавляется `{ file: "documentation/bff.html", target: "frontend/bff" }`.
Существующий renderPageRedirect уже сохраняет location.hash; новый механизм не нужен.

В собранном исходном HTML проверены пять ID: `bff-проверенная-часть`,
`что-наблюдается-на-проде`, `релизы-и-граница-доказательства`, `где-искать-реализацию`,
`что-еще-нужно-проверить`. Все сохраняются на новой странице ровно один раз.
Исторические секции могут стать вложенными заголовками с явными ID.

Дата, SHA, таблица наблюдений, источники и ограничения прежней проверки сохраняются.
Непроверенное в октябрьском отчёте не объявляется отсутствующим сейчас. Ссылки из
current-state, архитектуры и трека BFF переводятся на новый адрес/исторический якорь.
Старые URL с fragment проверяются на корневой и вложенной базе сайта.

## Источники и ограничения задачи

Страницы описывают код выбранного SHA, а не новый прогон продукта на проде. Наблюдения
прода сохраняют собственные дату/релиз/результат. Ссылки на код — SHA и проверенные строки.
Перед реализацией проверяется удалённый main: новый head изучается до обновления фактов,
имя локальной ветки само по себе не подтверждает свежесть.

Сборка должна назвать фактическую обработку TS/JSX, SVG, bundle и CSS выбранной версии
Vite. Дефолты подтверждаются исходниками установленной версии либо официальными
источниками. Наличие Babel в транзитивных зависимостях не доказывает преобразование
всего приложения через Babel. Соответствие формальному пункту РК не обещается;
добавление Babel или замена сборщика не входят в задачу.

У актуального frontend есть dev:prism и mockPrefer для проверок мутаций с If-Match.
Можно объяснить существующий режим со ссылкой на владельца. Не создаётся новый мок,
не меняется Apidog и не запускается sync ради документации. Описание Go-вызовов
относится к реализации выбранного SHA, не к аудиту сегодняшнего Apidog.
Ответ мока не доказывает сохранение в Go.

Изменения ограничены docs: 12 страниц, меню, ссылки, переадресация и проверки.
Код продукта, контракт и зависимости не меняются. OpenWiki не перегенерируется.
Legacy-режимы и требования безостановочного развёртывания не добавляются.

## Приёмка и проверки

1. Обзор и 11 подразделов доступны в согласованном порядке; соседи меню сохранены.
2. Сквозной сценарий объясняет редактор, autosave, очередь, hash и подтверждение.
   Touch/IME/лимит и новый ввод во время ответа описаны без противоречий коду.
   Все шесть схем из раздела «Глубина и форма» присутствуют на пяти страницах;
   проверены связи, пары с прозой, синтаксис, PNG и lazy-рендер в браузере.
3. Файлы и строки реальны, источники фиксированы на SHA; версии библиотек совпадают
   с lockfile. Современный main владельца не подменяет установленную версию.
4. BFF объясняет устройство и сохраняет историческое свидетельство. Старый адрес
   и пять якорей работают в корне и превью; внутренние ссылки ведут прямо к цели.
5. Тесты охватывают структуру, значимые факты, новые внутренние якоря и перенос;
   нет чувствительных данных и Markdown-ловушек. Проверен собранный HTML.
6. Проходят modules:check, typecheck, test и build. Без Docker — DIAGRAMS_NATIVE=1.
   Навигация/перенос проверены check-readability.ts hierarchy scroll для корня и
   вложенной SITE_BASE; новые Mermaid проверяются также секцией pages.
7. При дальнейшем PR указывается превью; после отдельно порученного слияния
   проверяются Pages и опубликованные страницы. Планирование не разрешает слияние.

## Выполнение

План строится по этой редакции. До реализации владелец выбирает
superpowers:executing-plans либо superpowers:subagent-driven-development.
Работа идёт этапами: проверка человеком, затем следующая задача только по его команде.
Готовые страницы Frontend добавляются в меню по мере появления, без ожидания задачи 6;
итоговое дерево и порядок остаются прежними. BFF остаётся отдельным пунктом до переноса
его страницы в задаче 3.
