# Eraser-схема первого HTML с пользователем — дизайн

Дата: 16.10.2026. Статус: содержание схемы согласовано в диалоге; письменная спека ожидает ревью.

## 1. Цель

На странице «Серверный bootstrap» нужна самостоятельная Eraser-схема, по которой студент может
проследить получение пользователя и его передачу в первый HTML до рендера интерфейса.
Схема показывает согласованный проект BFF, включая гостя и недоступность Go.
Она не меняет архитектуру из
[спеки bootstrap](./2026-10-16-bff-server-bootstrap-design.md).

Пользователь одобрил следующий состав: браузер → Caddy → HTML-хендлер BFF; общая с RPC сессия
и refresh → Go; локальный шаблон и `{ user }` → serialize-javascript → HTMLRewriter; готовый HTML
→ браузер → стор → первый рендер. Отдельно показаны `user: null` и HTML `503` с сохранением сессии.

## 3. Выбор представления

Расширение `bff-contract` сделало бы и без того общую схему подробнее, но оставило бы читателю
генерацию и сборку вперемешку с разбором первого запроса. Повторное встраивание этой схемы
на странице bootstrap не объяснило бы сериализацию, старт клиента и ошибки.

Выбрана отдельная `diagrams/modules/2/bff-bootstrap.json`, встроенная через
`<Diagram name="modules/2/bff-bootstrap" />` в начале раздела «HTML-запрос» после вводного абзаца.
Существующие схемы контракта и монорепы сохраняют свои задачи и адреса.
Сборка, публикация ассетов и откат не дублируются на новой схеме.

## 4. Содержание и границы

### Основной поток

1. Браузер отправляет GET HTML, включая переход по внешней ссылке. Cookie сессии — `SameSite=Lax`.
2. Caddy передаёт запрос HTML-хендлеру BFF.
3. Хендлер использует общую с tRPC обработку сессии, refresh и Orval-клиент Go. Новый отдельный
   механизм refresh и HTTP-вызов собственного endpoint tRPC не появляются.
4. При действительной сессии общий клиент получает DTO через Go `GET /users/me`.
   Возврат DTO на сторону BFF показан явно; Go не вызывает сериализатор или HTMLRewriter.
5. BFF сериализует только `{ user }` через `serialize-javascript` с `isJSON: true`.
6. Bun HTMLRewriter объединяет безопасный JSON и локальный `index.html` из образа BFF.
   Подпись шаблона поясняет: он прочитан и проверен при старте, хранится в памяти.
   Загрузки шаблона из S3/CDN на пользовательский запрос нет.
7. HTML `200` возвращается через Caddy в браузер. Обновление либо удаление cookie передаётся
   заголовками этого ответа до тела. Браузер читает JSON через `textContent` и `JSON.parse()`,
   инициализирует стор, затем выполняет первый рендер. Стартового RPC `users.me` нет.

Вставка подписана как `script#bootstrap`, `type="application/json"`; `setInnerContent` использует
`html: true` после безопасной сериализации. Серверное дерево React не изображается.
Клиентский старт показывается компактной цепочкой возле браузера, а не серверной обработкой.

### Гость и ошибка

- Нет сессии: отдельный путь к сериализации `{ user: null }`, Go не вызывается.
  Подтверждённо недействительная сессия также даёт гостя с удалением cookie, в том числе после
  отклонённого refresh или повторного `401` от Go. Эти случаи не подписываются как отсутствие
  любого обращения к Go; детальная политика остаётся в тексте.
- Сеть, таймаут, `5xx` или S2S-ошибка Go: отдельный HTML `503`, приложение не запускается,
  сессия сохраняется. Успешно обновлённая cookie приходит и с последующим `503`.
- Общая выноска: HTML `200` и `503`, включая гостевые, имеют `Cache-Control: private, no-store`.

Условия ветвей видны на связях либо в прилегающих выносках. Ошибка Go не ведёт в гостевой путь.
Токены, cookie и служебные ответы Go не изображаются содержимым bootstrap.

### Раскладка

Слева — нейтральный браузер с id `client`; внутри синей группы нашей инфраструктуры — Caddy,
BFF и Go. Вложенная группа BFF содержит обработку сессии, HTML-хендлер, сериализатор,
HTMLRewriter и локальный шаблон. Компоненты BFF не выглядят отдельными развёрнутыми сервисами.
Обозначение Go `GET /users/me` соответствует уровню описания текущей страницы.

Основной поток читается по нумерации; ветви гостя и `503` размещены отдельно от успешного пути.
Координаты абсолютные, кратны 20. Легенда справа, цвета и типы стрелок — по `scripts/colors.ts`.
Не вводятся собственные цвета статусов. Конкретные координаты выбираются при рендере и осмотре PNG.

## 6. Проверка

Структурные тесты закрепляют смысловые связи и размещение компонентов BFF; точные координаты
не проверяются. Ветки `{ user: null }` и `503` различаются, есть передача локального шаблона
в HTMLRewriter, оба HTML-ответа возвращаются через Caddy к браузеру.
Тест страницы проверяет точное имя `<Diagram>` внутри существующего раздела.

Обязательный цикл: validate → check → warm → render → осмотр PNG.
Визуально проверяются читаемость, границы групп, подписи и маршруты стрелок, различимость ветвей
и отсутствие впечатления, что данные рендерятся в React на сервере или шаблон запрашивается из CDN.
Перед коммитом выполняются `bun run modules:check`, `bun run typecheck`, `bun run test`,
`bun run build`. На собранном сайте проверяются новая встроенная схема, её HTML/PNG-ссылки и консоль.
После push проверяется превью PR.

Это проверка документации, не runtime-тесты будущего приложения. Порядок последующей работы —
ревью письменной спеки, план, SDD; ранее разрешённые коммит, push и обновление PR сохраняются.
