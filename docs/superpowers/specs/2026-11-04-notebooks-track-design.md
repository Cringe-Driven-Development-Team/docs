# Единая документация трека блокнотов во втором модуле

Статус: согласовано пользователем 2026-11-04. Выбран общий трек с подтреком редактора. Страницы сайта пока не изменены.

## Цель и границы

Дать студентам одну точку входа в план второго модуля: открытие блокнота, редактирование и сохранение ячеек, запуск окружения, исполнение и получение результатов. Показать границы ответственности фронта, BFF и бэка и возможность параллельной работы.

Это документация целевого поведения, а не подтверждение реализации или проверки прода. Полные критерии приёмки остаются в GitHub issues, HTTP-схемы — в Apidog, визуальные состояния — в Figma. В треке нужны объяснение взаимодействия и прямые ссылки, а не копии всех трёх источников.

## Рассмотренные подходы

1. **Общий трек с подтреком редактора — выбран пользователем.** Сохраняет самостоятельную область работы над редактором и даёт общую точку входа для сценария блокнота.
2. **Полное слияние треков.** Уменьшает число узлов, но убирает отдельный трек редактора и требует переноса привязок задач на доске. Отклонён в пользу первого варианта.

## Структура

- `file-exec.md`: название «Блокноты: редактор и исполнение», короткая подпись графа «Блокноты». Сохранить id, URL, area и текущих исполнителей.
- `monaco.md`: название «Редактор блокнота», `part_of: file-exec`. Сохранить id, URL, исполнителя и ментора. Актуализировать подзадачи #37 и #38.
- `file-exec/contract.md`: подстраница «Сохранение и исполнение» с согласованным взаимодействием клиента, BFF и Go. Зарегистрировать через `pages` и связать с обеими страницами треков.
- На главной странице: результат модуля, карта задач, границы и порядок работы, ссылки на редактор, описание взаимодействия, макеты и API.
- На странице редактора: базовая работа с ячейками и сохранением (#37), отображение (#38), передача состояния в исполнение (#51), явно отложенные удобства следующего модуля.

Одна дополнительная подстраница — предложение исполнителя: на ней удобно держать общие правила сохранения и запуска, не дублируя их между двумя треками. Новых треков и переезда опубликованных URL не требуется.

## Содержание

| Область | Граница ответственности |
| --- | --- |
| frontend#37 | Создание, изменение, удаление и перемещение ячеек; сырой код и Markdown; автосохранение, серверный хэш, последовательные мутации и сохранение черновиков при конфликте |
| frontend#38 | Подсветка Python и безопасный просмотр Markdown поверх редактора и сохранения из #37 |
| frontend#51 | Окружение, одиночный и массовый запуск, очередь, polling, результаты и восстановление состояния |
| Бэк | Серверное сохранение и контроль версии; сессии и исполнение; сохранённые результаты. Ссылки на backend#13 и задачи редактирования по проверенным актуальным ТЗ |

На странице взаимодействия описать:

- `notebooks.get` загружает блокнот и необходимые данные активной сессии; `cells.create/update/move/delete` обслуживают редактирование.
- #37 хранит подтверждённый текст отдельно от черновика, сериализует мутации и обновляет непрозрачный серверный хэш. BFF передаёт его в `If-Match`. При конфликте локальный текст сохраняется.
- #51 использует общий сигнал изменений и ожидание сохранения из #37 перед запуском. Отдельный `source_hash` относится к сохранённому исходнику запуска и не заменяет хэш блокнота.
- `runtime.updates` приносит состояние сессии, очереди, события и конкретные результаты исполнений. Получение нового вывода само по себе не требует перечитывания всего блокнота.
- Целевое правило: outputs, execution_count и output_truncated не меняют хэш редактирования. По проверке текущей сессии опубликованный Apidog ещё расходится с этим правилом; перед написанием страниц проверить снова и явно обозначить статус. Не представлять целевое правило уже реализованным.
- Результаты и признак усечения сохраняются для повторного открытия блокнота; безопасный вывод Markdown и результатов обязателен.

Сначала согласуется интерфейс состояния и сохранения #37. Разработку #51 можно начинать на фикстурах; интеграция использует основу #37. #38 и #51 выполняются независимо друг от друга: подсветка не блокирует исполнение. Реализация и проверка редактора не требуют готового импорта `.ipynb`; для первичной проверки используются фикстуры и согласованный API/Cloud Mock, для проверки сохранения — доступный бэк.

Автокомплит, мультикурсор и продвинутые команды остаются за рамками текущих задач. Не расширять эту работу до реализации редактора, runtime, новых API или перемещения задач между спринтами.

- Сохранить назначения, спринты, статусы и поле «Трек» доски. Не менять состав команды или инфраструктурные треки.

## Приёмка и проверка

Из модуля №2 доступен общий трек блокнотов, из него — редактор и описание взаимодействия. Старые адреса открываются. В затронутых страницах нет противоречий о read-only редакторе и переносе подсветки на следующий модуль. Разделены план, подтверждённые контракты и ожидаемые изменения.

Выполнить `bun run modules:check`, тесты данных модулей, `bun run typecheck`, `bun run test` и сборку по правилам репозитория. На собранном сайте проверить вложенность трека, ссылки и навигацию. В PR приложить превью. До реализации пользователь согласует эту спеку, затем план и способ выполнения по правилам сессии.
