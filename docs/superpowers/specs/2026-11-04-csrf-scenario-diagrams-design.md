# Диаграммы сценариев CSRF

## Цель и основания

На `/documentation/security/csrf` уже разобраны семь сценариев запросов и атак.
Пользователь указал, что тексту не хватает диаграмм, и показал Eraser-схемы
из документации модуля №2 как ориентир. Студент должен уметь объяснить защиту
на рубежном контроле: кто контролирует запрос, отправится ли cookie, где произойдёт
отказ и дойдёт ли выполнение до Go. Страница остаётся каноническим источником OpenWiki.

Пользователь отказался от наброска в браузере и поручил сразу написать дизайн.
Документ описывает предлагаемое решение; диаграммы и изменения сайта ещё не реализованы.

## Подходы

1. **Семь самостоятельных Eraser-схем — предлагаемый вариант.** По одной рядом
   с каждым сценарием, с едиными участниками и обозначениями. Соответствует показанным
   пользователем примерам, позволяет открыть конкретный сценарий отдельно.
   Цена — семь поддерживаемых исходников и более длинная страница.
2. Три объединённые Eraser-схемы по примеру модуля: свой клиент, чужой сайт,
   внешняя навигация. Меньше файлов, но поддомен, login CSRF и XSS снова придётся
   объяснять преимущественно текстом либо перегружать общую схему ветвлениями.
3. Семь компактных Mermaid sequence/flowchart. Проще сопровождение и автоматическая
   раскладка, но визуальный язык отличается от приведённого пользователем образца.

Первый вариант выбран автором дизайна как рекомендация, а не выдан за ранее
согласованный выбор пользователя. Согласование этого документа подтверждает
формат Eraser и охват всех семи сценариев.

## Страница и визуальный язык

В каждом из семи существующих H3: короткий вводный абзац → схема на ширину статьи →
остальные объяснения. Использовать штатный `<Diagram>`: масштаб, перемещение,
полноэкранный просмотр и ссылки на HTML/PNG. Две колонки «текст/схема» здесь
не вводить: несколько участников и развилки требуют ширины.

Сохранить семь якорей, таблицы cookie и Content-Type, источники, даты и границы
проверки. Текст должен оставаться достаточным для понимания без изображения;
существенные условия нельзя переносить исключительно в подписи схемы.
Существующая Mermaid в разделе «Проверки BFF» остаётся алгоритмом проверок;
новые схемы показывают путь конкретного сценария и его результат.
Страница XSS и её Mermaid не меняются.

Общие правила семи схем:

- Направление основного запроса слева направо: инициатор → браузер → обработчик
  BFF → Go, когда вызов действительно возможен. Варианты — отдельными дорожками
  либо коротким вертикальным разветвлением; временную последовательность не заменять
  одним ребром, пропускающим решающую проверку.
- Явно различать код страницы и браузер: код задаёт `X-CSRF`/credentials,
  браузер управляет cookie, Origin и Fetch Metadata. `HttpOnly` не означает
  «браузер не отправляет cookie по запросу JavaScript».
- На границе браузер/BFF подписывать конкретный HTTP-запрос и при необходимости
  tRPC-процедуру. Участок BFF → Go обозначать HTTP, не RPC. Успешная CSRF-проверка
  не обещает успешный вызов Go без нужной сессии, валидации и прав.
- Каждый остановленный путь завершается явно: «415 до контекста»,
  «403 csrf_invalid», «основной запрос не отправлен», «Go не вызывается».
  Не рисовать стрелку основного POST через BFF к Go после неуспешного preflight.
- Cookie подписывать условно и конкретно: доступная cookie, cross-site POST без неё,
  same-site запрос с `include`, top-level GET с Lax. Не изображать cookie
  передаваемой серверу атакующего поддомена.
- Caddy не повторять отдельным этапом в каждой схеме: публичный прокси-маршрут
  указан в тексте страницы. Показывать его только там, где он помогает разобрать
  доставку HTML. Это предложение автора дизайна, сохраняющее внимание на защите.
- Цвета, группы, иконки и легенда — существующие соглашения eraser-diagrams.
  Результат отказа выражается подписью, а не новой системой цветов.
  Легенда содержит только используемые зоны и типы связей.
- В узлах — короткие названия; условия — у соответствующих стрелок или развилок.
  Не копировать абзацы статьи в крупные текстовые поля схемы. Точные координаты,
  размеры и разрешённые иконки остаются исполнителю с проверкой готового PNG.

## Содержание семи схем

| Раздел и исходник | Что читатель должен увидеть |
| --- | --- |
| Наш клиент — `csrf-client.json` | POST `/api/trpc/notebooks.create` с JSON и `X-CSRF: 1`; браузер прикладывает доступную cookie при `same-origin`, задаёт Origin/Fetch Metadata. Адаптер принимает запрос, BFF проверяет CSRF, затем сессию/вход и вызывает Go при выполнении условий. Отдельно отмечен исход без сессии: `401`, без вызова Go. |
| Чужая форма — `csrf-form.json` | Атакующий задаёт action/поля/enctype; браузер отправляет cross-site POST без Lax-cookie и без `X-CSRF`. Для существующей POST mutation: urlencoded/plain → адаптер → `415`; multipart → контекст BFF → `403`. Оба пути без Go. Таблица форматов остаётся в тексте. |
| Чужой fetch — `csrf-fetch.json` | Две дорожки: простой GET `/api/trpc/users.me` без заголовка действительно отправлен и получает `403`, но CORS не даёт чужому JS прочитать ответ; JSON или `X-CSRF` → OPTIONS без cookie → нет CORS-разрешения → браузер не отправляет основной запрос. Не выдавать отказ preflight за ответ mutation. Простой POST объясняется соседним текстом и схемой формы. |
| Захваченный поддомен — `csrf-subdomain.json` | Инициатор на HTTPS-поддомене остаётся cross-origin, хотя same-site. Cookie приложения не уходит серверу поддомена, но может сопровождать запрос к приложению: у fetch нужен `include`. Простая форма без заголовка остановлена адаптером/CSRF; fetch с заголовком остановлен preflight. Проверки точного Origin и допустимого Sec-Fetch-Site подписаны отдельным резервным условием на случай ошибочного разрешения CORS, а не реально пройденным этапом этого заблокированного fetch. |
| Внешняя ссылка — `csrf-navigation.json` | Ссылка → top-level GET HTML с доступной Lax-cookie → Caddy/BFF → HTML-хендлер. Сессия есть: чтение пользователя, при необходимости refresh и данных открытого блокнота; сессии нет: Go для этих данных не вызывается. Возвращается HTML с bootstrap. Получение HTML не требует `X-CSRF`; последующие вызовы API проходят собственные проверки. |
| Login CSRF — `csrf-login.json` | Цель: привязать браузер жертвы к аккаунту атакующего, прежняя сессия жертвы не нужна. Компактный блок «Если бы вход не защищался» показывает предполагаемый результат: сессия атакующего → жертва сохраняет данные в его аккаунте. Отдельный фактический путь к `auth.login`: форма → `415/403`, JSON fetch → отказ preflight; Go и создание сессии не достигаются. Гипотеза и действующее поведение явно разделены подписями. |
| XSS в нашем origin — `csrf-xss.json` | Условие: JavaScript атакующего уже исполняется внутри origin приложения. Он ставит `X-CSRF`, браузер прикладывает cookie и корректные Origin/Fetch Metadata. CSRF проходит; защищённый вызов достигает Go только при действующей сессии, валидных данных и правах. Скрипт может читать ответ, хотя не может читать HttpOnly-cookie. Отдельная короткая подпись отсылает к защите bootstrap/выводу текста, без утверждения о наличии XSS-уязвимости. |

Различие поддомена и XSS объясняется самостоятельными схемами, не повторяется
полностью во всех остальных. Во внешней навигации не использовать старое утверждение
«bootstrap содержит только user»: текущая страница также описывает данные блокнота.
Refresh не представлять изменением предметных данных, но и не отрицать смену токенов.

## Размещение и источники OpenWiki

Предложение автора: исходники хранить в `diagrams/security/`, встраивать через
`<Diagram name="security/csrf-client" />` и аналогичные имена. Это тематические
схемы фактической документации, не планы модуля и не обзор инфраструктуры.
Семь схем не дублировать на странице «Архитектура».

В репозитории уже есть механизм папок вне архитектурного индекса: `HIDDEN_FOLDERS`.
Добавить в него `security`, уточнив комментарий: скрытие из общего индекса
не определяет статус «план/реализация». Отразить тематический каталог и семь схем
в README. Это ограниченное расширение существующего соглашения о размещении
схем, вместо семи новых обзорных разделов архитектуры; `ROOT_NAMES` сохраняется.

Сейчас OpenWiki принимает только корневые JSON схем. Синхронно добавить
`diagrams/security/*.json` в `scripts/openwiki-source-path.ts`, `.openwikiignore`
и описание корпуса `openwiki/INSTRUCTIONS.md`. Вложенные планы `diagrams/modules/**`
по-прежнему исключены. Изменение правил корпуса проверить тестами включения,
исключения и определения устаревшей wiki. Генерацию OpenWiki не запускать:
обновление источников не выдавать за обновление производных страниц.

Схемы модуля используются как визуальный материал, их файлы и страницы не меняются.
Обновления AGENTS.md или скиллов для реализации этой задачи не требуются:
размещение в тематической папке зафиксировано здесь как предмет согласования.

  `34ea7a9c042a3e2bcd2677be71fe380bc674fbfb`.
- В `site/documentation/security/csrf.md` одна Mermaid алгоритма и семь сценариев
  с явными якорями. Указаны SHA frontend, tRPC 11.19.0, результаты локальных проб
  и отдельно ограничения продовой проверки.
- В модуле существуют `bff-csrf-client`, `bff-csrf-foreign`, `bff-csrf-navigation`.
  Объединённая схема чужого сайта включает форму и preflight; отдельной схемы
  login CSRF/XSS нет. Схема навигации содержит устаревшее для текущей страницы
  ограничение bootstrap только пользователем.
- `Diagram` поддерживает вложенные имена; сборка уже рендерит вложенные JSON.
  `indexNames` исключает папки `HIDDEN_FOLDERS`; тест сверяет результат с `ROOT_NAMES`.
  Корпус OpenWiki отдельно ограничен `diagrams/*.json`, а не списком скрытых папок.

Перед реализацией подписей сверить используемые утверждения с конкретными исходниками,
на которые ссылается CSRF-страница. Если обнаружено изменение реализации, определить
его влияние на текст и схему; не обновлять даты продовых наблюдений из-за рендера.
Диаграммы визуализируют проверенный код и браузерные правила, но не свидетельствуют
о проведении авторизованных атак на проде.

## Приёмка и границы

- Во всех семи сценариях есть соответствующая схема. У каждого запроса видны
  условия cookie, этап остановки/продолжения и исход относительно Go.
- Формы `415/403`, preflight, same-site поддомен, внешний GET, login CSRF и XSS
  не смешаны; примеры используют существующие процедуры с допустимыми методами.
- Схемы валидны, соблюдают цвета, подписи читаются, линии не закрывают условия;
  каждый готовый PNG осмотрен. HTML и PNG открываются из просмотрщика.
- Проверены собранные страница и якоря на desktop/mobile, корне и базе превью;
  нет общего горизонтального переполнения. На мобильном доступно увеличение
  и перемещение схемы, а текст сценария читается без увеличения.
- Проходят typecheck, тесты, полная сборка и проверка ссылок. Регрессионные тесты
  покрывают существенные развилки схем и правила корпуса/индекса, не точные
  литературные формулировки каждого узла.
- Не меняются приложение, механизмы защиты, планы модуля и конфигурация прода.
  Отдельная обзорная схема границ инфраструктуры, новая тема сайта, библиотеки
  и дополнительные проверки атак с аккаунтами на проде в работу не входят.

## Статус

Независимая проверка полноты дизайна: существенных вопросов, мешающих составить
план, не выявлено.

Дизайн предложен на согласование. После одобрения — план реализации;
способ выполнения плана пользователь выбирает отдельно, если ещё не выбрал
его явно для этой задачи.
