# Документация редактирования и исполнения блокнотов

Статус: владелец выбрал `superpowers:executing-plans`; реализация выполняется в отдельной ветке.

## Задача

Дать команде полное описание блокнотов на основе интегрированного кода frontend/BFF,
backend и infra. Читатель должен проследить путь от открытия и редактирования ячейки
до исполнения Python, получения и сохранения результата. Текст описывает устройство
и поведение непосредственно, без истории переписки и перечня прежних вариантов.

Основание — поручение владельца, переданное из сессии «Проверь макеты и контракты
блокнотов». Недоступность прода не блокирует эту работу: документация имеет статус
проверки исходников, а не отчёта о работоспособности текущей выкладки.

1. Подсветка Python из PR170 уже в main. Источником документации служит интегрированный

2. Apidog GET content уже требует неизменности hash при изменении только результатов.
   Backend изменяет UUID revision при публикации нового результата. Старое утверждение
   обзора о том, что Apidog ещё требует обратного, больше не соответствует чтению контракта.
3. Backend освобождает пользовательский слот для STOPPED/FAILED, даже при незавершённой
   очистке. Требование макетов и описание stage в Apidog обещают удержание слота до очистки.
   Это разрыв реализации/требования; документация не выбирает новое продуктовое правило.
4. Есть разница между серверной очередью исполнения и фронтовой очередью сохранения,
   между завершением исполнения и projection результата, между hash блокнота и SHA-256 source.
   Эти различия должны быть объяснены на конкретном пути данных.
5. Выполнение, сохранение черновика, ошибка сети, конфликт и очистка — независимые состояния.
   Ошибка получения обновлений не означает отсутствия runtime, исчезновение из очереди
   не подтверждает успех, принятие stop не подтверждает удаление ресурсов.
6. Макеты всё ещё содержат старые надписи «В очереди», «Перейти к ячейке», длительность
   под счётчиком и имя другого блокнота. Поздние решения владельца из передачи и актуальные
   ТЗ имеют приоритет при описании целевого интерфейса; текущий код описывается отдельно.
7. Frontend#165, #172, #173, #35, #120, #42, #96 открыты. Наличие задачи не подтверждает
   реализацию. У #42 уже есть подробное ТЗ; фразу обзора «правила поиска не описаны» нужно
   заменить точной ссылкой, не расширяя эту работу до реализации поиска.
8. Текущий источник содержимого блокнотов — поячеечный PostgreSQL. S3 bucket сохраняется
   в infra, но текущий notebook repository его не использует. Факт выполнения миграции
   на проде не проверялся. Runtime-VPS отдельная для сессии; Go управляет provisioning,
   agent запускает Docker/kernel. Рабочие файлы kernel находятся во временном tmpfs.

Точные пути и строки для фактов переносятся в страницы из исследовательских отчётов,
с проверкой файла на указанном SHA. Публичные ссылки ведут на immutable GitHub blob.
Данные из Figma не подтверждают реализацию, а closed/merged не подтверждают выкладку.

### Рассмотренные способы размещения

- Переписать целевой контракт модуля в описание реализации: компактнее по числу маршрутов,
  но смешивает план с фактом и теряет смысл существующих ссылок на согласованные требования.
- Добавить одну большую страницу: проще навигация, но весь редактор, runtime, результаты
  и инфраструктура оказываются в одном длинном документе.
- Предлагаемые пять страниц: каждая отвечает на отдельный вопрос, сохраняет адреса плана
  и даёт одну каноническую точку описания текущего кода для каждой темы.

- Явно описать черновики удалённых ячеек (#165) и проверенный порядок выбора latest execution
  между вкладками. Баг не превращается в рекомендуемое продуктовое поведение.
- Сохранение результатов, источник истины и выгрузка S3 описываются по коду; старая диаграмма
  модуля остаётся целевой моделью с заметной ссылкой на актуальное устройство.
- Перечислить состояния сессии, исполнения и projection, причины и ошибки только из кода.
  Для каждого лимита указать, что именно ограничивается и где он применяется.
- Desktop/touch, отсутствие автокомплита, импорта, поиска или инспектора в UI описать по
  факту; серверная ручка инспекции сама по себе не означает панель переменных в приложении.
- Для Markdown и output описать действующие средства безопасного рендера, не заявляя
  прохождения XSS-регресса #35 или аудита изоляции.
- Добавить схемы из таблицы ниже существующими средствами сайта; не менять оформление

## Схемы

Обязательны две Eraser-схемы устройства и четыре Mermaid-схемы поведения.
Каждая показывает реализацию на зафиксированных SHA, а не проверенную выкладку.
Рядом — объяснение и ссылки на код; требования, расходящиеся с кодом, отмечены отдельно.

| Формат и источник | Размещение | Что объясняет |
| --- | --- | --- |
| Eraser: `diagrams/notebooks-components.json` | `notebooks/index.md` | Ответственность browser, Caddy, BFF, Go, PostgreSQL, provisioner и runtime-agent/kernel; путь запросов и данных |
| Eraser: `diagrams/notebooks-infrastructure.json` | `notebooks/storage-and-infrastructure.md` | Границы gateway/backend/runtime VPS, сеть и mTLS, Docker/kernel и временный tmpfs, постоянный PostgreSQL, отдельный исторический контекст S3 |
| Mermaid: `sequenceDiagram` | `notebooks/editing.md` | Черновик → очередь сохранения → BFF/If-Match → PostgreSQL; успешное подтверждение и конфликт с чтением свежей версии и явным выбором пользователя |
| Mermaid: `sequenceDiagram` | `notebooks/execution.md` | Save-before-run → принятие команды/очередь → agent/kernel; сохранение результатов backend и получение обновлений браузером через polling |
| Mermaid: `stateDiagram-v2` | `notebooks/execution.md` | Состояния сессии и удержание слота; STOPPED/FAILED освобождают слот до окончания отдельной очистки ресурсов |
| Mermaid: `flowchart` | `notebooks/results.md` | Snapshot → projection с проверкой source_version/latest attempt и лимитов → applied/conflict; повтор временной ошибки и сохранение истории исполнения |

На схемах нет прямого доступа браузера/BFF к agent/kernel и активной записи блокнотов
в S3. Очередь сохранения отделена от очереди исполнения. Завершение execution не является
условием начала projection: промежуточный результат тоже может быть applied, а следующий
снова pending. Изменение revision при публикации результата отмечено как разрыв с Apidog.
После разрешения конфликта запуск требует явного действия пользователя.

Eraser-схемы зарегистрировать в README, `ROOT_NAMES` и архитектурном разделе по правилам
репозитория; актуализировать существующие проверки реестра. Старую модульную схему
оставить целевой моделью с переходом к новым. Использовать существующие `Diagram`
и `DiagramSection`, не дублировать исходники схем между страницами.

Не входят исправления приложения/API, ремонт или проверка прода, запись в Figma/Apidog,
создание задач, комментарии, изменение инфраструктуры и генерация OpenWiki. Нет новых
требований legacy-совместимости, поэтапной выкладки или высокого uptime.

## Проверка результата

Каждое существенное утверждение имеет ссылку на точный SHA/строку либо явно помечено
требованием/неизвестным. Проверить переходы и меню собранного раздела, все локальные
ссылки и якоря, отсутствие реальных IP/CIDR/секретов и Vue-интерполяций.
Для Eraser пройти validate → check → warm → render и осмотреть PNG каждой схемы;
для Mermaid выполнить `bun run mermaid` и осмотреть рендер всех четырёх схем.
Проверить читаемость, подписи, стрелки и отсутствие обрезания на собранных страницах
в светлой/тёмной теме и на узком экране. Успешный парсинг не заменяет визуальную проверку.

Обязательные команды репозитория: `bun run modules:check`, `bun run typecheck`,
`bun run test`, `bun run build` (без Docker — `DIAGRAMS_NATIVE=1 bun run build`).
Для изменённого меню — browser checks `hierarchy scroll` по `docs-site`.
