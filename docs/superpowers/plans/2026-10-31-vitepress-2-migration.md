# VitePress 2 Documentation Migration Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Перевести docs на VitePress `2.0.0-alpha.21` с выпущенным module-graph и подтвердить работу опубликованного сайта.

**Architecture:** Точечно обновить движок и конфигурацию, сохранить текущую интеграцию Mermaid при успешной проверке. Сначала проверить docs с локальным архивом обновлённого module-graph вне исходного workspace, затем подключить его фактическую версию из npm и проверить CI/сайт.

**Tech Stack:** Bun, Node >=22.22.0, VitePress `2.0.0-alpha.21`, Vue, Mermaid, существующий Eraser pipeline, Docker/Chromium, GitHub Pages.

**Spec:** `docs/superpowers/specs/2026-10-31-vitepress-2-migration-design.md`.

## Global Constraints

- Спеки согласованы 2026-10-31; перед реализацией пользователь выбирает executing-plans или subagent-driven-development.
- VitePress в docs закреплён точно на `2.0.0-alpha.21`.
- В задачу включены пакет `@tp-prepare/vitepress-module-graph`, его выпуск через существующий workflow и интеграция опубликованной версии.
- Поддержку старого движка, редизайн и новые возможности страниц не добавлять.
- Сохранить адреса, формат данных, схемы, русские подписи и поиск.
- Сохранить Mermaid `securityLevel: strict`, размеры/прокрутку и поведение якорей.
- Менеджер — Bun; итоговые manifests/lockfiles не содержат локальных tarball/file/workspace-ссылок.
- Посторонние прямые зависимости не обновлять, изменения транзитивного графа проверить.
- Схемы Eraser и их формат не переделывать; реализация в отдельных worktree.

## Review Focus

1. Mermaid после гидратации и SPA-перехода: SVG появляется, тема меняется, якорь остаётся под видимой шапкой — Task 2, шаг 5.
2. Вложенный base превью: поиск, JS/CSS, iframe схемы и ссылки остаются под `/branches/vitepress-2/` — Task 2, шаги 4–5.
3. Graph SSR прошёл, но клиент не получил данные: фильтр/карточка/шапка действительно работают — Task 2, шаг 5.
4. CSS reset: кнопки масштаба и полного экрана Eraser остаются доступны, узкое меню читаемо — Task 2, шаг 5.
5. Локальный архив скрывает расхождение с npm: чистая установка опубликованной версии повторяет успех — Task 3, шаги 2–3.

## Карта файлов

- `package.json`, `bun.lock`: точный движок и итоговая опубликованная версия module-graph.
- `site/.vitepress/config.mts`: новое имя настройки копирования кода; существующие поиск, sidebar, base, noExternal и Mermaid.
- Только при доказанной регрессии: `site/.vitepress/theme/index.ts`, `custom.css`, `Diagram.vue` и соответствующие существующие тесты в `scripts/`.
- `README.md`: обновить упоминания старой версии/команд, только если они есть.
- `.github/workflows/ci.yml`, `pages.yml`, `scripts/build-vitepress.ts`, `check-site.ts`, `check-mermaid.ts`: существующие пути проверки; менять лишь при конкретной несовместимости.
- План пакета хранится в `TP-Prepare/frontend-packages/docs/superpowers/plans/2026-10-31-vitepress-2-module-graph.md`; его технические задачи не дублировать здесь.

## Порядок между планами

1. Task 1 координирует подготовку пакета по его собственному плану, Task 1.
2. Task 2 docs проверяет локальную интеграцию и проходит отдельное ревью кода.
3. Затем выполняется Task 2 плана пакета (выпуск) и его ревью; Task 3 docs подключает npm-версию и проходит своё ревью.
4. Task 4 интегрирует docs и проверяет реальную публикацию. До выпуска пакета этот PR не сливать.

Локальная разработка docs и пакета независима; точка совместной проверки — готовый архив. Каждый кодовый результат проходит ревью по выбранному пользователем способу; завершение публикации не заменяет ревью реализации.

### Task 2: Обновить docs и проверить локальную интеграцию

**Files:** `package.json`, `bun.lock`, `site/.vitepress/config.mts`; условные исправления из карты файлов.

**Interfaces:**
- Consumes: архив Task 1 с подтверждённым SHA-256 и прежние экспорты module-graph.
- Produces: проверенные изменения docs для целевого VitePress и локального архива, без file-ссылок в коммите. В основной рабочей области module-graph пока остаётся текущей опубликованной версии; это промежуточный commit, не готовый к merge. Финальную зависимость установит Task 3. Новых публичных функций не вводится.

- [ ] **Шаг 1: Обновить движок и конфиг.** В `package.json` установить `vitepress: "2.0.0-alpha.21"`, выполнить `bun install`. В `config.mts` заменить только `markdown.codeCopyButtonTitle` на `markdown.codeCopyButton: { tooltipText: 'Копировать код' }`; остальные действующие настройки сохранить. Проверить изменения lockfile. Временно оставшийся старый module-graph не является итоговой зависимостью и не подтверждает интеграцию.

- [ ] **Шаг 2: Подготовить временного потребителя архива.** Во временном каталоге вне workspace воспроизвести текущие исходники docs, включая изменения шага 1, без `.git`, `.claude/worktrees`, node_modules, cache и dist. Сохранить структуру скриптов/страниц. Скопировать архив внутрь этой копии и установить его по относительному пути: абсолютный путь хоста недоступен при Docker mount в `/work`. Установить точный VitePress через Bun; подтвердить фактические версии и SHA-256 архива. Временные file-ссылки допустимы только в этой копии. Копию можно использовать для локальных исправлений/повторной проверки до выпуска; изменения исходников переносить обратно в рабочую область.

- [ ] **Шаг 3: Проверить текущий Mermaid plugin и исправить наблюдаемые сбои.** В потребителе запустить typecheck, тесты, `modules:check` и полный build существующими командами. Проверить dev. Peer-warning Mermaid записать отдельно от ошибок выполнения. Если плагин работает, оставить. Если воспроизведён дефект — сначала тест/воспроизведение с ожидаемым результатом, затем минимальное исправление и повторная проверка; не ослаблять `securityLevel` и проверки ссылок, не убирать прокрутку к якорю ради зелёной сборки. Существенный рост интеграции вынести на уточнение спеки.

- [ ] **Шаг 4: Проверить production под обоими base.** С корневым base использовать `bun run build`. Для вложенного base передать переменную внутрь контейнера явно: текущая обёртка `scripts/docker.ts` не передаёт host env. Из каталога временного потребителя:

  ```sh
  docker build -t docs-vitepress-2-check .
  docker run --rm -e SITE_BASE=/branches/vitepress-2/ -v "$PWD:/work" -v docs-vitepress-2-check-modules:/work/node_modules -w /work docs-vitepress-2-check bash -c 'bun install --frozen-lockfile && bun run build:native'
  ```

  На Git Bash учесть `MSYS_NO_PATHCONV=1` из правил репозитория. Без Docker допустим `SITE_BASE=/branches/vitepress-2/ DIAGRAMS_NATIVE=1 bun run build` с настроенным Chromium. Проверка `site:check` должна завершаться `site ok`, ссылки/якоря/ресурсы — существовать; в собранном HTML проверить именно префикс `/branches/vitepress-2/`. Сохранить логи. Подавать результат каждой сборки браузеру под соответствующим префиксом, а не открывать вложенный build как корневой. Продовый Docker wrapper ради этой проверки не расширять.

- [ ] **Шаг 5: Проверить браузер в dev и production.** Использовать следующие сценарии; зафиксировать результат, URL, тему и ошибки консоли в журнале выполнения:

  | Страница/действие | Ожидаемый результат |

Для исправления выявленной логики добавить регрессионную проверку в ближайший существующий тест; отдельную браузерную инфраструктуру заранее не создавать.

- [ ] **Шаг 6: Зафиксировать локально проверенный код.** Перенести исправления из временного потребителя в рабочую область. Не переносить его file-ссылки: в основном package.json пока оставить прежний module-graph, с целевым VitePress и соответствующим lockfile. Проверить diff, зафиксировать код коммитом `chore(site): перейти на VitePress 2.0.0-alpha.21` и пройти task review по результату локального архива. ### Task 3: Подключить выпущенный пакет из npm

**Files:** `package.json`, `bun.lock`; при выявленной регрессии — конкретный файл из Task 2 и его тест.

**Interfaces:**
- Consumes: принятый результат Task 2 docs, результаты локальной интеграции для выпуска пакета и `MODULE_GRAPH_VERSION`/release commit из package plan.
- Produces: итоговый docs на целевом VitePress и опубликованном module-graph, registry-only lockfile, успешные проверки конечной установки.

- [ ] **Шаг 1: Выпустить проверенный пакет.** Передать результаты локальной интеграции в Task 2 package plan; выполнить штатный выпуск после его проверок. Получить фактический `MODULE_GRAPH_VERSION`, release commit и успешный publish run. Перед продолжением завершить Task 2 пакета и его task review; это самостоятельная операция выпуска после принятого кода.

- [ ] **Шаг 2: Подключить реестр в настоящей рабочей области docs.** Установить `@tp-prepare/vitepress-module-graph@<MODULE_GRAPH_VERSION>` точной версией через Bun, обновить lockfile. Подтвердить в манифесте установленного пакета точный VitePress peer. Чистую установку `bun install --frozen-lockfile` проверить в отдельной временной копии с этими конечными manifest/lockfile, без установленного локального архива. В итоговом diff не должно быть временных путей и непреднамеренных изменений прямых зависимостей.

- [ ] **Шаг 3: Закрыть интеграционные проверки и зафиксировать изменение.** Повторить typecheck, тесты, modules:check и полный build с финальной зависимостью из npm; браузерные сценарии Task 2, шагов 4–5 подтвердить на этом результате. Обновить только устаревшие инструкции README, если найдены. Проверить diff, пройти ревью по выбранному способу, затем commit `chore(site): перейти на VitePress 2.0.0-alpha.21`. Не коммитить generated dist, временный потребитель или артефакты локальной установки.

### Task 4: Интегрировать docs и проверить опубликованный сайт

**Files:** исходники не менять, кроме устранения конкретного дефекта проверки; `.github/workflows/pages.yml` и CI использовать существующие.

**Interfaces:**
- Consumes: принятый commit Task 3, опубликованный `MODULE_GRAPH_VERSION` и результаты проверок.
- Produces: merge SHA docs, успешный Pages deploy, проверенный `https://docs.cellestial.ru/` с целевой сборкой.

- [ ] **Шаг 1: Подготовить PR и проверить превью.** PR в `Cringe-Driven-Development-Team/docs/main`, описание по шаблону репозитория с проверками и ссылкой на `https://docs.cellestial.ru/branches/docs-vitepress-2-migration/`. Убедиться, что превью показывает нужный head, а не только успешный dispatch; проверить последующий Pages run на main и список веток. При отказе превью по бюджету времени зафиксировать причину и использовать уже проверенную локальную сборку по правилам репозитория.
- [ ] **Шаг 2: Интегрировать актуальный head.** Перед merge проверить обязательные CI, отсутствие конфликтов и свежесть head. Следовать пользовательскому разрешению bypass без отдельного ожидания апрува, если GitHub допускает merge. После merge проверить результат и post-merge CI/Pages; не считать dispatch подтверждением выкладки.
- [ ] **Шаг 3: Проверить прод.** На `https://docs.cellestial.ru/` повторить граф/карточку, трек/подстраницу, Mermaid, Eraser, поиск и якорь ниже схемы. Записать merge SHA, ссылку на успешный Pages deploy, время проверки и результаты. При подтверждённом дефекте исправить его и повторить затронутые проверки; миграцию не объявлять завершённой при сломанном сайте.

## Уточнение границ задач при исполнении

Ruling: исходный Task 2 разделён на локальную интеграцию и конечную установку из npm, чтобы каждая кодовая задача прошла своё ревью до следующей операции выпуска/merge; цель, scope и приёмка спеки сохранены. Если это решение окажется неверным, стоимость — дополнительная передача контекста между двумя небольшими задачами.

## Самопроверка плана

- Контракт версии, минимальный scope и ограничения — Global Constraints и Task 2.
- Пакет, упаковка, dev/SSR и выпуск — package plan; локальная и npm-интеграция — Tasks 2–3.
