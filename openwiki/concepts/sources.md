# Где искать ответ

Начинайте с `AGENTS.md` и README рабочего репозитория. Для вопроса на границе компонентов открывайте [«Контекст проекта»](https://github.com/Cringe-Driven-Development-Team/docs/blob/d8efbac41672d36ddd2db295f057f84c87eabfe3/site/project-context.md#L9): эта страница распределяет виды сведений по владельцам. OpenWiki — производный тематический указатель, канонические документы остаются в `docs`. [Карта вопросов](../quickstart.md) помогает выбрать тематическую страницу, затем нужно перейти по её ссылке на исходник.

| Вопрос | Владелец и проверка |
| --- | --- |
| Как компонент работает сейчас | Его код, конфигурация и тесты на актуальном SHA; для состояния продакшена дополнительно стенд. |
| Как устроен HTTP API Go | Контракт в Apidog; реализацию сверять с кодом backend. |
| Какова общая архитектура | [Текущие разделы сайта и схемы MVP](../architecture/mvp.md), затем код затронутых компонентов. |
| Что предстоит сделать | `site/modules/` и утверждённые проектные документы; это план, пока реализация не проверена. |
| Где жить спеке и плану реализации | В репозитории, где выполняется задача; в `docs` отражают общие решения. |
| Как вести PR и задачи | Правила команды в репозитории `.github`; локальные инструкции конкретного репозитория имеют свой предмет. |

Эти границы заданы [таблицей источников](https://github.com/Cringe-Driven-Development-Team/docs/blob/d8efbac41672d36ddd2db295f057f84c87eabfe3/site/project-context.md#L13).

## Текущее, историческое и целевое

Разделы сайта вне `site/modules/` и корневые схемы описывают текущее состояние по документации. Модули и старые спеки/планы фиксируют намерения либо историю решений. Завершённый трек остаётся историей, а описание действующего продукта выносят за пределы модулей. Замороженные `diagrams/frozen-k3s/` не становятся текущей архитектурой из-за наличия файлов. [Правило разделения](https://github.com/Cringe-Driven-Development-Team/docs/blob/d8efbac41672d36ddd2db295f057f84c87eabfe3/AGENTS.md#L21); [пояснение проекта](https://github.com/Cringe-Driven-Development-Team/docs/blob/d8efbac41672d36ddd2db295f057f84c87eabfe3/site/project-context.md#L30).

Ссылка из `docs` на чужой репозиторий с фиксированным SHA подтверждает только прочитанную версию. Например, раздел текущего CSRF указывает конкретные снимки backend и frontend; это полезное свидетельство, но не автоматическое подтверждение их нового `main`. Чтобы установить факт реализации, нужно открыть актуальный код и тесты, а для продакшена проверить стенд. [Формулировка правила](https://github.com/Cringe-Driven-Development-Team/docs/blob/d8efbac41672d36ddd2db295f057f84c87eabfe3/site/project-context.md#L36).

Если источники расходятся, сначала сравните SHA и свежесть клона; затем исправьте документ, которому принадлежит этот вид сведений. Для API-маршрута см. [отдельную страницу](../workflows/api-contract.md), для свежести wiki — [проверку checkpoint](../documentation/wiki-freshness.md).
