# Модуль №3

## Карта сценариев блокнота в FigJam

Это руководство для будущей организации существующих макетов Cellestial в карту сценариев.
Сейчас экраны на странице Release собраны длинными рядами: по ним трудно увидеть переходы,
развилки, ошибки и способы продолжения работы. Карта должна связать экраны с действиями
пользователя и сделать пограничные случаи видимыми команде разработки.

Согласованный подход — нативная карта FigJam. Здесь описаны её устройство и порядок создания;
сама доска ещё не создана, полный реестр случаев не собран. Изменение макетов, реализация
поведения сервиса и встраивание редактора карт в Cellestial в эту работу не входят.

### Что хранить в Figma Design и FigJam

Figma Design остаётся источником экранов, компонентов, стилей и вариантов. Исходные фреймы
с Release не удаляют и не переносят ради карты. Реорганизация самой Release требует отдельного решения.
FigJam содержит карточки состояний и нативные редактируемые подписи, стрелки и таблицы.
Одно превью длинного ряда экранов не заменяет карточки отдельных состояний.

В каждой карточке состояния нужны короткое название, превью конкретного экрана, ссылка
на исходный Figma node (source-node URL) и ID иллюстрируемых случаев. Если экрана нет,
карточку явно подписывают «Макет отсутствует»: это не разрешение придумать экран или
объявить его реализованным. Ссылка всегда ведёт к редактируемому оригиналу.

Превью — снимок, автоматическая синхронизация с Design не обещается. После изменения экрана
команда обновляет снимок и затронутые связи. Снимок помогает читать карту, исходный node —
проверять и редактировать макет.

### Организация доски и первый охват

В FigJam одна бесконечная страница; карту организуют секциями. Предлагается один файл
«Cellestial — сценарии» в той же командной папке, где находятся макеты. Точное имя и папку
выберут при создании карты. Для подготовки этого руководства право записи в Figma не требуется.

Входная секция содержит назначение карты, границы покрытия, источники и ссылки на секции
групп сценариев. Легенда объясняет обозначения состояния, перехода, альтернативной и ошибочной
ветки, отсутствующего макета и открытого вопроса; смысл не должен зависеть только от цвета.
На входе виден статус разбора каждой группы.

Начальная навигация следует группам на скриншоте макетов: вход и регистрация; список,
загрузка и удаление блокнотов; работа внутри блокнота; исполнение; поиск; профиль;
подключение и отключение 2FA; вход с 2FA; выход из сессий; офлайн-режим.
Это первоначальная группировка, а не проверенный полный каталог файла.

Первый подробный разбор ограничен блокнотом. Остальные группы остаются в навигации
с пометкой «не разобрано», без подробной карты входа, профиля, 2FA, списка блокнотов,
поиска и офлайн-режима. Открытие блокнота — вход в этот разбор; потеря доступа или
авторизации — выход в соответствующий сценарий, без проектирования всего входа.

| Секция блокнота | Что в ней показать |
| --- | --- |
| Путь пользователя | Открыть → подготовить/изменить → сохранить → выполнить → понять результат → вернуться к работе. Для каждого этапа: цель, действие, ожидаемый результат и ссылки на подробные схемы |
| Редактор и сохранение | Действия с ячейками, подтверждение сохранения, ошибки, неоднозначные ответы и разрешение конфликтов |
| Окружение | Подготовка, готовность, занятость, завершение, простой и очистка |
| Исполнение и результаты | Одиночный и массовый запуск, очередь, итоги, вывод, сохранение результатов и возвращение после потери связи |
| Покрытие и вопросы | Реестр случаев и сочетаний состояний, недостающие экраны и нерешённые вопросы |

Краткий путь пользователя — верхний уровень journey map (CJM): он объясняет цель и связь
этапов. Подробные схемы переходов раскрывают действия и развилки внутри этапа. Эмоции
и боли не записывают как исследованные факты без пользовательских данных.

### Случаи, переходы и покрытие

Основной путь идёт последовательно; альтернативные и ошибочные ветки располагают рядом
с соответствующим переходом. На стрелке пишут действие или событие и условие, в состоянии —
что видит пользователь и что он может сделать дальше. Технический код ошибки может
подтверждать основание, но не заменяет пользовательское объяснение.

Для каждой ошибки нужен способ продолжения, ожидание внешнего результата либо явно открытый
вопрос. Соседство фреймов на Release само по себе не доказывает переход. Неподтверждённый
переход не изображают как установленное поведение.

Рядом со схемами ведут таблицу покрытия: одна запись на случай, со стабильным ID, который
также указан на карточках состояний. Поля записи:

| Поле | Содержание |
| --- | --- |
| ID случая | Стабильный идентификатор, например `NB-CONFLICT-01` |
| Исходное состояние | Что уже известно об окружении, исполнении, сохранении и связи |
| Событие и условия | Действие пользователя или внешнее событие и условия перехода |
| Наблюдаемый результат | Что пользователь видит после перехода |
| Продолжение | Доступное действие, ожидание либо открытый вопрос |
| Источник требования | Точная ссылка на требование, описание сценария или прототип |
| Экран | Ссылка на исходный node; отсутствие макета отмечено отдельно |
| Статус основания | Требование / гипотеза / вопрос / противоречие |
| Готовность реализации | Отдельный признак: известность требования не доказывает готовность кода |

Будущие реализацию и тесты связывают с ID случая. Наличие карточки не означает прохождения
теста. Недостающий экран и неизвестное поведение — разные пробелы.

Следующие группы — обязательная инструкция для будущего сбора, а не уже заполненный
каталог всех исключений:

| Группа | Что извлечь из источников и связать с экранами |
| --- | --- |
| Открытие | Сохранённые исходники и результаты, ошибка обязательного чтения, повторное открытие во время работы сессии |
| Редактирование | Python/Markdown, создание, удаление и перемещение ячеек, новый ввод при незавершённом сохранении, ограничения ввода и количества ячеек |
| Сохранение | Черновик, ожидание, подтверждение, ошибка, неоднозначный ответ; раздельное сохранение текста и результатов |
| Конфликт | Получение свежего снимка и его ошибка, оба выбора версии, закрытие без выбора, повторный конфликт, удалённая на сервере ячейка |
| Окружение | Отсутствие сессии, подготовка, готовность, ошибка запуска, другая активная сессия, завершение, простой, незавершённая очистка |
| Исполнение | Сохранение перед запуском, QUEUED/RUNNING, фиксированный состав массового запуска, новые правки, изменение порядка, пустой набор code-ячеек, переполнение очереди |
| Результат | Успех, ошибка кода, остановка, UNKNOWN, усечение вывода, поздний результат изменённой ячейки, ошибка сохранения outputs |
| Восстановление | Потеря связи, возвращение, перезагрузка, другая вкладка, повторное действие, отсутствие автоматического повторного запуска |

Состояния окружения, исполнения, сохранения и связи рассматривают независимо. Допустимые
сочетания проверяют таблицей решений: для сочетания указывают условия, ожидаемое действие
и основание. Невозможные сочетания исключают с обоснованием, неизвестные оставляют
вопросами. Отдельный полный экран для каждого сочетания не требуется.

### Пример: запуск при конфликте сохранения

Это пример целевого поведения из [контракта сохранения и исполнения](/modules/2/tracks/file-exec/contract),
а не свидетельство проверки прода. При готовом runtime и выполненных остальных условиях
запуска кнопки запуска ячейки и «Запустить всё» остаются доступны; для массового запуска нужны code-ячейки.

1. При неразрешённом конфликте нажатие запуска открывает общий диалог конфликта.
   Команды `runtime.execute` и `runtime.executeAll` не отправляются. Если конфликт возник
   во время ожидания сохранения, эта попытка запуска тоже отменяется.
2. Фронтовая очередь сохранения приостановлена, несохранённые черновики остаются отдельно.
   Загружается свежий серверный снимок с hash и ячейками; до его получения выбор версии
   недоступен. Ошибка загрузки оставляет блокнот и черновики видимыми, доступно «Повторить».
3. «Загрузить серверную версию» предупреждает о потере несохранённых изменений:
   редактор принимает серверный снимок, отбрасывает локальные правки и старую очередь.
   «Сохранить мой текст» предупреждает о замене текста затронутых ячеек: их исходники
   сохраняются последовательно со свежим hash, затем с hash подтверждённого ответа;
   остальные серверные изменения сохраняются. Успех показывается после подтверждения сервера.
4. Крестик, Escape или клик по фону закрывают диалог без выбора. Конфликт остаётся
   нерешённым, очередь сохранения приостановлена; плашка и «Разрешить конфликт» позволяют
   вернуться к диалогу. Закрытие и получение снимка не подтверждают сохранение черновиков.
5. Повторный конфликт требует нового снимка и того же диалога. Удалённая на сервере ячейка
   автоматически не воссоздаётся, её черновик доступен для копирования. Старые удаления
   и перемещения не воспроизводятся автоматически.
6. После успешного выбора любой версии нужен новый клик запуска. Сохранённое намерение
   запуска не выполняется автоматически. Уже принятая сервером очередь исполнения
   продолжает работать независимо от диалога.

На карте у каждого исхода должны быть свой случай, экран или отметка его отсутствия
и продолжение. Обычный запуск без конфликта ждёт сохранения и выполняется в рамках
того же нажатия; требование нового клика относится к отменённой попытке.

### Источники и вопросы перед наполнением

Основа для сбора — [общий сценарий блокнота](/modules/2/tracks/file-exec),
[редактор](/modules/2/tracks/monaco), [сохранение и исполнение](/modules/2/tracks/file-exec/contract)
и [окружения](/modules/2/tracks/notebook-vps). Это документы целевого состояния;
макеты и требования сами по себе не доказывают поведение прода.

Инвентаризируют только нужные секции с точными fileKey/nodeId. Для каждого перехода
проверяют требование, описание сценария или прототип. Расхождения регистрируют,
не выбирая молча удобный источник. Проверенный 12.11.2026 срез макетов ограничен
разделом исполнения `581:16814` файла `7iaVDGiwzQk2vZIB5ogVlq`; общий аудит файла не проводился.

Уже известные вопросы сохраняют видимыми:

- Мобильные макеты исполнения описывают чтение и запуск, а трек редактора включает телефон
  360 px в проверку ввода. Возможность редактирования на телефоне нужно явно сверить.
- В контракте зафиксировано расхождение семантики hash на 04.11.2026 между целевым правилом
  и тогдашними API/backend. Нужно проверить актуальное решение; старое наблюдение
  не доказывает текущий дефект.
- Контракт не гарантирует сохранность локальных черновиков после перезагрузки.
  Восстановление очереди исполнения не означает восстановления несохранённого текста.

### Как агенты будут создавать и проверять карту

1. Агент собирает реестр экранов, требований и случаев с точными ссылками.
2. Независимый агент проверяет покрытие, сочетания состояний и противоречия.
3. Владелец принимает недостающие продуктовые решения; гипотезы остаются видимыми.
4. Один агент создаёт или обновляет согласованные секции FigJam, сохраняя ручные правки.
5. Проверка читает ноды и соединители, сверяет таблицу покрытия и скриншоты, проверяет
   переходы к исходным макетам. Проверку полноты и визуальную проверку фиксируют отдельно.

Используют имеющийся официальный MCP, `figma-ops`, `figma-use` и `figma-use-figjam`, предварительно
читая актуальные схемы инструментов и инструкции. Для первой карты не требуются новый MCP,
отдельная CJM-платформа, собственный plugin или генератор. Создание карты потребует права
редактирования выбранного файла; наличие MCP этого права не доказывает.

### Приёмка будущей карты и методические источники

При отдельной работе по созданию карты проверяют:

- Секции и навигация охватывают перечисленные группы, подробный разбор начинается с блокнота;
  границы разбора и статусы остальных групп видны на входе.
- Карточки связаны с оригиналами Design, содержат снимки и ID случаев; отсутствующие макеты
  отмечены явно. Подписи и связи редактируются в FigJam, снимки обновлены после изменений экранов.
- Переходы имеют условия и основания, ошибки — продолжение, ожидание или открытый вопрос.
  Таблица покрытия и таблица решений согласованы со схемами, противоречия не скрыты.
- Пример конфликта отражён со всеми исходами; восстановление связи, очереди и черновиков
  различается. Известность требования, готовность реализации и результат теста не смешаны.
- Отдельно зафиксированы проверка структуры и покрытия, визуальный осмотр и проверка ссылок
  на исходные макеты. Карта не объявлена полным каталогом случаев без проверки.

Это руководство задаёт назначение, границы и правила для отдельного плана создания карты;
оно не подтверждает готовность доски. Методические источники:
[официальный skill FigJam](https://github.com/figma/mcp-server-guide/blob/main/skills/figma-use-figjam/SKILL.md),
[Plugin API для FigJam](https://developers.figma.com/docs/plugins/working-in-figjam/),
[инструменты MCP](https://developers.figma.com/docs/figma-mcp-server/tools-and-prompts/),
[различие user journeys и user flows](https://www.nngroup.com/articles/user-journeys-vs-user-flows/).
Они объясняют способ работы с картой, но не свидетельствуют о готовности Cellestial.
